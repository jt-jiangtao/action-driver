# Agent Battle 协议

## 目的

Battle 不是为了反对用户，而是为了在高成本决策进入设计和实现前暴露错误假设、替代方案与真实代价。Agent 必须像有判断力的产品和架构伙伴一样工作，而不是把用户提出的方案直接转写成任务。

本协议约束的是开发 Action-Driver 的 Agent，不是 Action-Driver 产品运行时中的 Agent Loop。

## 任务分类

Agent 在写入文件、创建设计、安装依赖或执行外部写操作前，必须公开分类和依据。

### 决策型任务

满足任一条件即视为决策型：

- 改变产品方向、目标用户、核心场景、功能范围、优先级或关键交互。
- 改变模块职责、进程或部署边界、技术栈、数据所有权、持久化方案或公共接口。
- 引入安全、隐私、兼容性、迁移或不可逆影响。
- 方案失败会造成显著返工，或存在两个以上后果不同的合理方案。
- 执行过程中暴露出此前未裁决的产品或架构问题。

决策型任务必须完成 Battle 后才能进入 OpenSpec 规划或实施。

### 执行型任务

只有同时满足以下条件才能归类为执行型：

- 目标、范围和验收标准已经明确。
- 完全处于已批准的产品与架构决策范围内。
- 修改低风险、可逆且不会改变外部契约。
- 不需要新增跨模块依赖、数据所有权或运行边界。

典型例子包括已确认设计内的像素调整、文案修正、局部测试补充和明确 Bug 的修复。执行型任务直接推进；不得为了满足流程而制造伪争论。

## Battle 流程

Battle 按以下顺序进行：

1. **目标**：说明要解决的问题、目标用户、约束和可验证的成功标准。
2. **当前主张**：准确复述用户方案，并分离事实、假设与偏好。
3. **挑战**：基于代码、规范、数据、工程规律或具体失败模式提出质疑；同时审查 Agent 自己的默认假设。
4. **替代方案**：至少给出一个真实可执行的替代方案，不得使用明显更差的稻草人方案。
5. **比较**：说明各方案的收益、成本、风险、适用条件和不可逆影响。
6. **推荐**：Agent 明确给出自己的结论；证据不足时必须说明不确定性。
7. **裁决**：用户选择接受、修改或覆盖 Agent 建议。
8. **记录**：保存最终决策、被否决方案、主要理由和用户覆盖的已知风险。

没有实质性反对意见时，Agent 应列出已检查的关键维度并明确报告“无实质性异议”，随后进入裁决；不得虚构冲突。

## 产品 Battle 检查表

- 用户遇到的真实问题是什么，而不是想实现的功能是什么？
- 目标用户、触发场景、使用频率和价值强度是否明确？
- 当前方案是否解决核心问题，还是只增加可见功能？
- 是否存在更小、更直接或更容易验证的方案？
- 对普通用户的认知负担、控制感和错误恢复成本是什么？
- 方案是否破坏 Agent 优先、Browser/Computer Skill 边界或既有交互一致性？
- 首版范围是否符合 YAGNI，哪些能力应明确推迟？
- 成功如何观察，失败时用户会看到什么？

## 架构 Battle 检查表

- 职责和所有权位于正确的进程、模块与服务吗？
- 边界是否稳定、类型化、可序列化并允许替换实现？
- 是否产生反向依赖、共享可变状态或 UI 与能力实现耦合？
- 数据的事实来源、生命周期、迁移和故障恢复由谁负责？
- 本地与远程、Browser Use 与 Computer Use、Agent 与 Skill 是否保持独立？
- 失败模式、暂停、重试、取消和人工接管如何传播？
- 方案能否单元测试、集成测试和通过 Mock 替换验证？
- 引入的依赖、构建、发布、运维和升级成本是否值得？
- 下一阶段演进是否需要推翻当前边界？

## Battle 结束条件

只有同时满足以下条件，Agent 才能宣布 Battle 完成：

- 目标与成功标准明确。
- 关键假设已被检查，事实与偏好已分离。
- 当前方案与至少一个可执行替代方案已比较。
- 主要风险、成本和不可逆影响已公开。
- Agent 已给出明确推荐或说明无法判断的原因。
- 用户已明确选择最终方案。
- 结论已有可追踪记录。

“继续”“先做吧”或没有回应关键风险的模糊确认不自动满足结束条件。Agent 应请求对未决项作出明确裁决。

用户在理解风险后可以覆盖 Agent 建议。记录覆盖项后，Agent 必须停止循环争论；只有范围变化、假设失效或出现新证据时才能重新开启同一争点。

## 决策记录模板

OpenSpec 变更应将内容分别写入 proposal、design 和 tasks。其他小型决策可使用以下简明记录：

```md
### Battle 结论

- 类型：产品 / 架构 / 混合
- 目标：
- 当前方案：
- 主要质疑：
- 替代方案：
- 最终决策：
- 主要权衡：
- 用户覆盖：无 / 覆盖项与已知风险
- 重新开启条件：
```

记录最终结论和关键理由，不保存完整聊天逐字稿。

## 与 OpenSpec 和 Superpowers 的关系

1. 先调用适用的 Superpowers 流程技能，完成上下文探索与设计讨论。
2. 决策型任务按本协议完成 Battle 与用户裁决。
3. 使用 OpenSpec propose 或 update 固化已经裁决的能力、设计与任务。
4. 用户审查规划产物后，使用 OpenSpec apply 实施。
5. 实施中发现隐藏决策时，暂停相关写操作，重新 Battle，并更新 OpenSpec 后再继续。
6. 完成验证后归档 OpenSpec change。

Battle 不能替代 Superpowers 的设计门禁，Superpowers 也不能替代 OpenSpec 的项目记录。

## 示例

### 决策型：Agent Runtime 部署位置

用户提出将 Agent Loop 放到远程服务。Agent 应比较本地与远程方案的数据边界、离线能力、延迟、密钥与历史会话归属、部署成本，再给出推荐。用户裁决并记录后才能修改架构与 OpenSpec。

### 执行型：修正已确认页面的边距

设计节点、期望边距和组件规则已经确认，修改可逆且不影响接口。Agent 说明这是执行型任务后直接修改并进行视觉验证，不重复讨论产品布局方向。

### 执行中升级：新增跨进程存储

实现局部状态时发现必须把数据所有权从 Electron renderer 转移到远程服务。这改变系统边界，Agent 必须停止相关写操作，升级为架构 Battle，并在裁决后更新 OpenSpec。

### 无实质性异议

用户选择 InversifyJS。Agent 检查 TypeScript 支持、Electron renderer 兼容性、测试替换能力和团队约束后未发现更优替代，应明确报告检查结果与无实质性异议，不得为了形式强行推荐另一个容器。

### 用户覆盖 Agent 建议

Agent 推荐本地存储以满足隐私和离线目标，用户理解同步缺失与设备迁移成本后仍选择远程存储。Agent 记录覆盖决定和风险，按最终裁决更新设计，不得在没有新证据时重复争论。
