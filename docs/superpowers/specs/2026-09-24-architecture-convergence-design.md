# ActionDriver 架构收敛设计

## 目标与验收标准

本设计覆盖已审查出的事件顺序、故障恢复、进程职责、传输迁移、分包、重复基础设施与可观测性问题。目标是在保留现有产品能力的前提下，使本地 Runtime 成为任务与配置的唯一事实来源，让 Desktop Main 只承担本地能力与进程托管，让 Renderer 只负责查询、订阅和展示。用户要求所有已识别问题均进入实施范围；下文阶段仅表达依赖顺序，不表达可放弃的优先级。

验收时，两个任务的事件交错写入仍能分别实时显示和重放；进程在模型输出或工具执行中途退出后，任务有确定的终态且保留已提交内容；重启、重连、旧数据库迁移和打包运行所得视图一致；所有业务调用走明确的 HTTP/WS 契约；每份配置和日志只有一个权威写入方；无消费者的抽象和纯绑定容器已移除；现有 UI 与本地能力行为保持一致。

## Battle 结论与决策记录

- 类型：架构决策。涉及跨进程边界、持久化事件协议、数据所有权、公共包和依赖选型。
- 当前主张：用户允许完整重构，要求修复所有已发现问题，并优先确认可用三方库替代手写通用设施。
- 已核查假设：完整重写并非修复流顺序的必要条件；全局 SQLite 自增 `cursor` 是全库提交位置，不能作为单个请求的无间隙序号；LangGraph checkpoint 仍有真实用途，另一个未被生产消费的 checkpoint 抽象没有；新库不能替代任务语义、崩溃恢复与原生能力隔离。
- 可执行方案 A：一次性重写 Runtime、Desktop、数据库与 UI。边界最整齐，但旧数据和功能回归风险最大，且会与现有 HTTP/WS、Skill、日志迁移工作重叠。
- 可执行方案 B（推荐并获用户确认）：按持久化可靠性、传输及所有权、包和实现简化、诊断与完整验收的依赖顺序收敛；每阶段有兼容迁移与回归门槛，最终完成全部范围。
- 可执行方案 C：维持双 RPC/HTTP 通道并局部修补。短期改动少，但配置及任务所有权继续分散，不能满足目标。
- 最终裁决：采用方案 B；使用 Hono、`@hono/zod-validator`、TanStack Query 和 `fast-check` 的明确用途；保留 SQLite、LangGraph、现有 OpenAI SDK 与 `ws`。用户分别确认了总体方向及三方库取舍。
- 用户覆盖：要求不按优先级删减审查范围。已知代价是迁移期较长、数据库协议和打包回归成本较高；用阶段验收限制风险。
- 重开条件：发现新证据表明现有进程边界无法支撑本地能力隔离，或迁移会不可逆地损坏已有数据。

这项决策覆盖 `docs/superpowers/specs/2026-09-24-activity-event-order-design.md` 中“全局 cursor 是唯一顺序权威、无需第二序号”的结论。后者对单请求串行事件成立；并发请求共享全局 cursor 时会产生请求内空洞。实施时须同步修订相关 OpenSpec 及协议文档，避免两套互相矛盾的规范并存。

## 目标边界

```text
Renderer ── HTTP 查询/命令 + WS 事件 ──▶ Runtime 服务
   │                                      ├─ 任务/会话/模型与 Skill 定义
   │                                      ├─ LangGraph、事件日志、SQLite
   │                                      └─ 原生能力请求 ──▶ Desktop Main
   │                                                           ├─ Browser / Computer
   └─ Electron 安全引导接口 ────────────────▶ Desktop Main       └─ 本机文件与权限
```

Runtime 负责任务状态机、模型和提示词配置、Skill 定义、事件与 SQLite 写入。Main 负责 Runtime 进程托管，以及需要 Electron/操作系统权限的 Browser、Computer 和本机文件能力。Runtime 通过类型化的能力接口请求 Main 执行；能力执行的事实由 Runtime 入库。Renderer 只查询 Runtime、订阅事件并运行纯投影，不写权威任务状态。Main 的引导/进程控制 IPC 可以保留；旧业务 MessagePort RPC 在对应 HTTP/WS 路由迁移和验证后删除，避免长期双写。

迁移本机 prompt、Skill 文件时，Runtime 通过文件存储端口持有定义和写入决策，Main 提供受权限约束的本机文件适配器。历史路径读取与一次性导入须幂等，不能让两个进程同时成为定义的权威写入者。远程 Runtime 演进时，Browser/Computer 仍由本机 Main 执行，不能将本机 GUI 权限扩散到云端。

## 事件协议、顺序与重放

每条持久化请求事件同时具有稳定 `eventId`、`requestId`、请求内连续 `sequence` 和全库单调 `cursor`。`cursor` 只用于数据库定位、保留范围和传输水位；Renderer 对单个请求只按 `sequence` 连续应用，按 `eventId`/`(requestId, sequence)` 去重。活动、文本、工具与终态事件均参与同一请求序列，不另设会互相竞争的连续展示计数器。工具条目仍以首次生命周期事件确定位置，后续状态按 `callId` 更新。

Runtime 在同一 SQLite 写事务内分配请求的下一个 `sequence` 并插入事件；数据库约束 `UNIQUE(request_id, sequence)`，成功提交后才广播。`stream_requests` 的最后序号与事件插入必须原子更新，跨写入路径只能使用一个事件追加入口。允许不同请求的全局 cursor 交错，不允许单个请求的序号缺失、重复或倒退。取消、失败、完成事件也经过此入口。

客户端对乱序到达的请求事件做有界缓冲；缺号时按最后已应用的全局 cursor 请求该请求的增量重放，不能将更大 cursor 当作连续序号。重复帧不会二次改变投影。重放使用 `(request_id, cursor)` 索引和有界分页，不能全表扫描后在内存中过滤。历史事件只读取时，按同请求 cursor 顺序映射成逻辑序号；数据库迁移应在事务中回填并加唯一约束，若历史数据不完整则从一致性快照恢复，不猜测丢失事件。

快照在同一一致性读视图里取得投影、该请求最后 `sequence` 及全局高水位 `cursor`。客户端先替换本地投影，再接收高水位之后的事件；若快照前已经缓冲事件，只保留序号大于快照最后序号的部分。服务端无法覆盖请求的重放缺口或客户端缓冲达到上限时，重新取快照。协议变更需版本化，并在旧客户端/旧数据库的受支持迁移路径上明确拒绝不兼容版本。

## 生命周期与崩溃恢复

Runtime 内只有一处任务生命周期状态机。LangGraph checkpoint 保存推理过程恢复信息，但不直接代表用户可见任务终态；事件日志与持久化任务记录由同一服务协调。投影是纯 reducer，Renderer 不根据网络断连自行宣告任务完成或失败。

Runtime 启动时，在接受新订阅/命令前扫描持久化的 `running` 请求与任务。如果没有仍活着的执行者，在事务内追加带下一请求序号的 `runtime.interrupted` 终态事件并将任务标记失败；保留已提交的文本、工具结果和 checkpoint，不自动重新执行模型或可能产生副作用的工具。重复启动不重复追加终态。待审批任务保持已有明确的待审批语义；其迁移/失效规则须与现有审批记录一致。用户之后可以显式重试为新请求，原请求保持可审计。

执行期异常、取消、能力调用超时都必须经同一状态机发出终态，且只发一次。模型输出已提交、工具执行结果尚未提交的崩溃窗口不能宣称工具未执行；恢复视图应标记该调用状态未知，并避免自动重试。工具调用须携带稳定调用标识，以便日志、人工判断和未来可幂等能力实现关联。

## 传输、三方库与包结构

HTTP 服务使用 Hono 路由和 `@hono/zod-validator` 校验输入，继续复用已有 Zod schema；Node 适配器和现有 `ws` 承担本地服务与流事件。统一生成或共享路由输入/输出契约，错误响应保留机器可读 code 与用户可读 message。HTTP/WS 均沿用当前本机认证、来源检查及敏感值脱敏规则，迁移不能拓宽访问范围。完成业务路由覆盖后移除旧 RPC DTO、preload 业务转发和 Main 代理；只留 Electron 必需的安全引导接口。

Renderer 用 TanStack Query 管理模型、任务、Skill 等异步读取的缓存、加载、失效与重试。流事件仍由独立订阅器喂给纯投影；写命令成功后按相关 query key 失效，不把实时增量硬塞进通用查询缓存。`fast-check` 用于请求事件交错、重复、乱序、断线/重放和重启状态机的性质测试。保留现有 LangGraph、SQLite、OpenAI SDK 和 `ws`；本阶段不引入 Socket.IO、XState 或 ORM，因为它们不负责持久化任务语义，替换成本高于现有收益。

包边界按消费者和依赖方向收敛：

| 单元 | 保留职责 | 迁移或删除 |
| --- | --- | --- |
| 跨进程契约包 | 可序列化的 HTTP/WS DTO、事件 schema、能力接口与版本 | 移出 React 投影、实现类、旧 MessagePort 业务 DTO 和 DI token |
| Runtime | Graph、模型适配器、任务状态机、SQLite、事件服务、定义存储 | 接收 `model-connections` 的实现；删除无生产消费者的 `ProjectionService` 和额外 `CheckpointStore` 抽象，保留实际 LangGraph checkpointer |
| Desktop Main | 安全引导、Runtime 进程托管和原生能力执行 | 迁出模型业务逻辑及定义权威写入 |
| Renderer | 页面、查询、订阅和纯投影 | 移入原在共享包的 UI 投影；合并重复的去重与生命周期判断 |
| 可观测性 | 跨进程只共享轻量事件类型；Node SDK 留在运行进程 | 避免 Renderer 引入 Node 实现；按实际消费者决定是否保留单独包 |
| 设计 token | Desktop 唯一消费的样式 | 合入 Desktop；日后出现第二消费者再提取 |

各进程改用显式工厂/构造函数注入真实边界接口。现有容器仅绑定已构造对象的地方删除 Inversify 和 `reflect-metadata`；若发现动态插件构建等真实容器用途，则先用明确工厂覆盖测试再移除。大文件按状态机、事件仓库、订阅、投影等职责拆分，避免再建一层无用途的接口/包装。

## 诊断数据所有权

SQLite 保存任务、工具、审批和用户可见事件事实。LangSmith 是模型调用日志的唯一来源，沿用已裁决的模型日志方案；OpenTelemetry 记录进程、HTTP/WS 和能力执行的运行诊断。不得把同一模型调用同时作为 Phoenix 和 LangSmith 两份权威记录。关联标识使用 task/request/call ID；密钥、令牌、原始敏感参数和不必要的屏幕内容不进入日志。诊断服务不可用不能改变任务状态或阻断工具执行。

## 实施顺序与验收

1. **可靠性基础**：引入请求内序号、原子追加、索引、迁移、纯投影及崩溃恢复；先在旧传输上验证并发与重放。
2. **传输与所有权**：Hono/校验接管 HTTP 路由，补齐 WS 契约、配置与 Skill 的 Runtime 所有权、Main 能力端口；逐条删除旧业务 RPC。
3. **包与实现收敛**：移动模型实现与 UI 投影，合并单消费者 token，删除无消费者抽象及绑定容器；TanStack Query 接管读取态。
4. **诊断收敛**：统一 LangSmith、OTel、SQLite 的边界和关联字段，清理重复模型追踪。
5. **全量验收**：完成单元、性质、集成、Electron E2E 与 macOS 打包冒烟；修订现有 OpenSpec、架构文档及迁移说明，并归档完成的 change。

每阶段都要覆盖旧数据库迁移、回滚前备份和协议兼容检查；一旦数据迁移已提交，回滚应用版本不应无说明地读取新 schema。性质测试覆盖两请求 cursor 交错、序号缺口、重复与乱序帧、截断重放、快照交接、终态唯一性；集成测试在模型流与工具调用中途杀进程并重复启动；E2E 核对任务页和 Skill/模型配置的既有操作；打包测试确认本机能力、连接认证与诊断开关均可工作。所有要求完成后才可宣称架构收敛完成。

## 风险与取舍

- 事件 schema 回填可能遇到历史缺口或不一致记录。迁移前备份，逐库验证唯一性，失败时保留原库并提供快照/只读恢复路径。
- 切换 HTTP/WS 和定义所有权时存在短期双通道窗口。每项能力以单写入方、可观测调用量和兼容测试为删除旧路径的门槛。
- 崩溃时未知工具结果无法被软件可靠推断。显式呈现未知状态与人工重试，比自动重放副作用更安全。
- 新增 Hono 与 TanStack Query 有依赖及学习成本。只用于其擅长的路由校验和读取态，不将其扩展为任务状态机。
- 现有未提交的 HTTP/WS、日志及 Skill 工作较多。实施前应核对并吸收这些改动，不能覆盖或假设其已完成。
