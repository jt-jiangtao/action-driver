# 工具调用直接执行设计

## 目标与验收

Action-Driver 的本地任务不再因工具审批停在输入框上方。模型请求本轮已启用的工具时，Runtime 完成注册、授权列表、名称和参数校验后立即排队执行；任务页仍按原有顺序显示工具、输入输出、失败、取消和最终正文。

验收以真实文件工具、受限 Shell 和 SearXNG Web Search 为对象：三者均无需用户点击即可从 `proposed` 进入 `queued`，成功或失败后模型能够续跑；未知或未启用的工具仍不可执行；取消、超时、日志和刷新后历史恢复不回归。

## Battle 结论

- 类型：架构与安全约束。
- 当前方案：移除交互式工具审批，已注册且获本轮授权的工具直接执行。
- 证据：当前 `RuntimeToolPolicy` 对 Shell、非低风险及网络工具返回 `require_approval`，`ToolInvocationService` 因而进入 `waiting_approval`；Desktop、WebSocket 和协议分别承载审批 UI、命令和状态。
- 替代方案：只自动执行低风险工具，Shell 和 Web Search 继续逐次审批。它保留人工拦截，但不能满足无阻塞执行目标。
- 最终决策：用户确认直接放行；保留工具发现白名单、定义与参数校验、Sandbox、执行超时、取消和审计，不将“放行”扩展为执行未注册或未授权工具。
- 主要权衡：模型可能受错误或恶意内容诱导，自动读取工作区数据或将敏感内容放入搜索查询；本地工具边界仍降低可触达范围，但不再提供逐次人工拦截。
- 用户覆盖：接受逐次人工拦截消失的风险。
- 重新开启条件：增加具有文件写入、任意命令、任意网络发送等新副作用的工具时，必须另行审查能力授权与隔离边界。

## 设计

### Runtime

`RuntimeToolPolicy` 保留工具注册版本、授予列表和模型名称一致性检查；通过检查后只返回 `allow`，不再按风险或副作用返回 `require_approval`。`ToolInvocationService` 仍校验输入、创建持久化调用、按 `proposed → queued → running → completed|failed|cancelled` 发布事件，保留 AbortSignal、超时和聚合日志。移除等待批准的 Promise、批准/拒绝方法及其调用入口。

当前 Sandbox Shell 的命令及参数白名单、只读文件边界不变；SearXNG 仍是单独的网络工具，并只调用配置的本地服务。工具授权列表不是人工审批：未授予的工具不会被发现或执行。

### 协议与历史

新任务不产生 `tool.waiting_approval`，也不接受 approve/reject 控制命令。新的公开调用状态去掉 `waiting_approval`。已持久化的旧事件与工具记录仍需可读取，供历史任务回放；兼容层只做读取映射，不向当前任务重新发出审批请求。若升级时发现实际仍悬挂的旧审批，保守地结束为取消/失败，不能在重启后替用户自动执行旧调用。

### Desktop

删除输入框上方的工具审批条、批准/拒绝按钮和相应客户端命令。任务过程保留工具行、展开的原始 I/O、失败及取消状态。旧历史中的等待审批状态以只读终态说明呈现，不提供可操作审批按钮。

### 验证与迁移

先将既有“等待批准”单元和 E2E 用例改为“自动执行”失败测试，再修改实现。覆盖未知工具、无授权、参数不匹配、超时、取消、Web Search、历史审批快照读取和完成后刷新。同步更新 `agent-tool-runtime`、`agent-task-experience` 的 OpenSpec 规范，以及仍引用逐次搜索审批的未归档变更；不重写已归档历史记录。
