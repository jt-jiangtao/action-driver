# 单次生成多于四张图片的设计

## 目标与成功标准

用户一次要求生成 5–16 张图片时，Agent 可以通过一次 `image.generate` 调用提交全部独立提示词。对话从工具开始运行起为每张图片保留固定插槽；Runtime 同时向默认生图模型发送最多 4 个请求，其余排队。每张成功图片在原插槽出现，部分失败与取消不会丢失已成功图片。用户要求超过 16 张时，Imagegen Skill 指导 Agent 分成多次调用。

本次不改变用户上传图片的数量上限、图片提供方接口、会话资产目录或图片字节不进入事件的规则。

## Battle 结论

- 类型：产品范围与 Runtime 公共接口变更。
- 用户主张：需要保障多于 4 张的生图请求，而非依赖现有 Skill 自行拆分的提示。
- 已核查：当前工具输入 schema、执行器校验、流协议 `imageCount`、工具事件及快照和 Skill 文案均限于 4 张；画廊可以按 `imageCount` 生成插槽。执行器目前一次同时启动全部请求，工具总超时 180 秒，提供方单请求超时 120 秒。
- 替代方案：保持每次最多 4 张，由 Agent 发起多次工具调用。实现改动较小，但 Agent 可能只调用第一批，无法稳定承诺一次请求全部完成，多个调用的结果也难以作为同一批次核对。
- 最终决策：用户确认单次最多 16 张、每次调用最多 4 张同时生成、其余排队；超过 16 张由 Agent 分批调用。保留每张固定插槽以及已成功资产。
- 主要权衡：单次任务可能延长并产生更多生图费用；多个独立工具调用各自最多 4 个请求，并非跨任务或跨调用的全局限流。
- 用户覆盖：无。
- 重新开启条件：提供方的实际速率限制低于并发 4，或产品需要跨调用统一的费用与并发预算。

## 决策与实现边界

### 工具输入与调度

`image.generate` 的 `images` 数组接受 1–16 个 `{ prompt }` 项，保持现有每个提示词的校验。先验证完整输入与默认模型，再启动任何网络请求；第 17 项必须在网络请求前被拒绝。执行器只保持最多 4 个活动请求，某个请求结束后立即启动队列中的下一项，直到全部结束或任务取消。结果沿用原始数组索引，完成顺序不改变显示位置。单个失败记录为该插槽失败，其他请求继续；全部失败时工具整体失败。

每个提供方请求继续保留 120 秒超时。工具总超时提升至 600 秒，使 4 波各 120 秒的最坏情况仍有持久化余量。取消时不再启动队列中的请求，活动请求收到同一 `AbortSignal`，取消后不产生新资产。已有成功资产仍保留。

### 事件与画廊

`imageCount` 的流事件与快照 schema 上限从 4 改为 16；工具状态在运行前写入准确张数。画廊依据调用 ID 和原始索引一次创建 1–16 个固定插槽，沿用两列及窄屏单列布局。未完成插槽显示占位动画；已有资产按索引替换；工具终态未收到资产的插槽显示失败或取消。助手文字始终位于画廊上方。事件、日志与快照只传张数、索引和资产引用，不传提示词或图片字节。

旧记录的 1–4 张载荷与没有 `imageCount` 的历史记录继续可读。用户上传图片仍维持单条消息最多 4 张，与生图数量上限分离。

### Skill 与提示词

系统 Imagegen Skill 明确一次调用可提交 1–16 个独立提示词，同一次调用内部最多 4 个请求并发；超过 16 个提示词时按顺序拆为多次工具调用。Skill 不声称上传图片、编辑图片或额外模型参数受支持。

## 验证

- 输入边界：4、5、16 项可执行，17 项在网络前被拒绝；普通工具事件不携带 `imageCount`。
- 调度：16 项时活动数始终不超过 4，结束一项才启动下一项；乱序完成仍保留索引。部分失败、全部失败、取消和超时分别检查最终状态与已保存资产。
- 对话：5 张和 16 张先出现等量插槽，逐张原位替换；失败、取消、快照恢复、历史重开时数量与文字顺序稳定，减少动态效果偏好仍生效。
- 随包 Skill 文案、主规范、类型检查、单元测试、构建及 macOS 打包冒烟验证同步更新。

## 风险与非目标

默认模型的费用和速率限制由提供方决定，排队只能限制单次工具调用的峰值，不能保证提供方接受全部请求。提供方持续失败时，失败插槽应明确显示；不重试或静默追加费用。此版不提供用户可调并发数、跨工具调用的全局调度器或逐插槽排队文案。
