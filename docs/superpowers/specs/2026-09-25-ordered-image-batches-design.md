# 生图批次与文字按调用顺序展示

## 目标与成功标准

生图结果应占据调用发生时的位置。一次任务先后调用多次 `image.generate` 时，批次按调用顺序排列；每批的 1–16 张图片按请求索引排列，完成先后只更新原插槽。最终助手文字出现在它实际生成的位置，不会因任务结束、断线恢复或重开历史而从图片下方跳到上方。生成前及批次之间的过程文字仍遵循现有规则，归入可展开的任务过程；只有最终回复文字作为普通助手消息显示。

本次不改变用户上传图片在气泡中的展示顺序、生图并发上限、提供方接口或会话文件目录。

## 根因

`AgentResponse` 固定先渲染 `message.content`，再渲染单个 `ImageGallery`。`normalizeAssistantParts` 将所有文字合并为第一项，再按图片到达时首次见到的调用 ID 分组。Runtime 在收到工具资产时才把图片加入消息，终态又用最终文本重建为“文字、所有图片”；桌面流投影在内容事件及结束事件重复相同的重排。因此目前的“图片总在文字下面”是多层共同实现的旧规则，而非单处 CSS 问题。目前 AgentGraph 顺序执行工具调用，但显示数据不应依赖这一执行细节；若将来并行执行，按资产到达顺序推断批次位置会出错。

## Battle 结论

- 类型：产品交互与消息公共接口变更，属于决策型。
- 用户目标：图片与最终文字按生成过程的实际顺序展示，多批生成稳定排序。
- 已核查：现有主规范明确要求文字统一在图片上方；现有代码、测试和历史快照均执行该规则。过程文字已由活动时间线归档，不能简单把全部流式文字当作最终回复。
- 推荐并获用户裁决：每次生图调用开始时固定批次锚点；批次按调用顺序，批内按请求索引，文字按实际生成位置穿插。过程文字继续归档。
- 真实替代方案：把所有图片统一放在全部文字上方。它只需调整展示和规范，但批次之间的文字无处安放，也无法表达真实调用时序，故未采用。
- 主要权衡：需要扩展消息内容和流事件协议，并同时修改 Runtime 持久化及桌面投影；旧消息没有批次锚点，只能保留其现有可恢复顺序，无法推算过去丢失的时序。
- 用户覆盖：无。
- 重新开启条件：产品决定让过程文字也常显在最终回复中，或要求把旧记录重建为无法从数据证明的调用时序。

## 设计

### 消息中的批次锚点

在助手消息的 `parts` 中增加一个只包含调用 ID 和请求数量的 `image-batch` 项。Runtime 处理某个 `image.generate` 的运行事件时插入一次锚点，并以相同事务保存助手消息和可重放的批次事件。批次事件位于任何该调用的图片事件之前；它不携带提示词或图片字节。工具没有真正进入运行态时不产生生成中占位卡。

已生成图片仍以现有带 `generation.callId/index` 的资产引用保存。收到图片后只追加或更新对应资产，不移动批次锚点。归一化只合并相邻文字、去除重复锚点和重复图片；不得跨批次合并文字，也不得根据图片完成时间重排批次。`contentIndex` 指向实际内容位置，桌面流投影按批次事件、文字事件及图片事件更新同一有序 `parts`。

### 最终文字与过程文字

流式文字保留它在当前消息片段中的位置。模型最终结束时，以终态内容校准最后一段最终文字，清除前几轮已归档到任务过程的文字片段，保留全部批次锚点和图片引用。因此“生图后再回答”的结果为图片在上、最终文字在下。任务过程仍保持原有折叠规则。

历史消息没有 `image-batch` 项时，按已经持久化的 `parts` 顺序展示图片；缺少调用索引的图片按记录顺序展示。旧记录不做破坏性迁移，也不伪造调用顺序。

### 画廊与恢复

`AgentResponse` 顺序渲染内容项，遇到批次锚点就渲染该调用独立的画廊。画廊一开始即按 `imageCount` 建立固定插槽；图片按 `generation.index` 填入，失败或取消只改变对应空插槽状态。无锚点的旧图片使用独立兜底画廊。各批次相互独立，后一批先完成也不能插到前一批之前。

快照、事件重放和本地历史都从同一份有序内容读取。重连发生在批次运行、部分图片完成、最终文本生成或任务终态时，顺序均不得改变。恢复时若工具状态存在但锚点尚未送达，依据已持久化批次事件恢复，不以图片完成顺序重建。

## 验证

- 合约：相邻文字合并，跨批次文字保持分隔；重复图片、乱序完成及多批调用均不改变锚点顺序。
- Runtime：两次调用，第二批图片先完成；批次事件先于该批任一图片；终态、取消和快照保留相同 `parts` 顺序。
- 桌面：开始时立即显示批次插槽；每张图片原位替换；最终文字位于最后一次生图批次之后；批次间文字按有序内容显示；重连与历史重开无跳位。
- 兼容：旧记录无锚点仍可看；用户上传图片气泡顺序不受影响；事件和快照不包含图片字节。

## 风险与边界

新增内容项和流事件要同步更新 Runtime、协议校验、桌面投影与测试。Runtime 写入锚点及对应事件必须原子化，否则崩溃可能产生工具已运行但消息缺少占位的短暂不一致。旧记录此前已把文字和图片重排，原始时序不可恢复；兼容只能保证可读和稳定。此版不改变过程文字的归档策略，不引入跨调用的全局生图限流。
