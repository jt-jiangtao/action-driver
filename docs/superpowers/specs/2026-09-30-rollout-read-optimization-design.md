# Rollout 读取与续读优化设计

## 目标与边界

本轮先改善长会话的请求查找、断线续读和重开时的读取成本。用户要求全部直接在 `main` 处理，并确认保守方向：维持每条日志写入后的 `fsync`、现有 Stream 协议、日志格式及崩溃恢复行为。桌面启动体积、占位图片和 Monaco 属后续独立变更。

## 当前状态

`RolloutSessionStore` 对任务和幂等键反复线性扫描请求 Map。`listForRequestAfter` 每页从会话开头重新折叠并派生事件，而实时发布和重连会连续调用该入口。`readRollout` 一次分配剩余文件大小的 Buffer，解析后的行又保留在会话运行时中。这些是代码路径上的重复成本，尚不是已经量化的用户延迟。

## 方案

1. 先对实际 rollout store 建立固定长会话基准，分别测请求查找、首次续读、连续分页、重开与内存峰值，保存修改前后中位数和 P95。
2. 把请求主 Map 与任务、幂等键辅助索引交给一个更新入口管理，启动时从投影重建。
3. 单请求派生事件在连续分页中复用；连续追加只补入新行，元数据或游标失配时从日志重新派生。缓存设硬上限，超限回退现有读取路径。日志始终是唯一事实源。
4. 仅在基准证明全文件 Buffer 明显提高重开峰值时，改用分块读取；解析后的历史行仍保持现有生命周期。

每项性能改动须在相同环境下使目标路径至少改善 20%，并保持实时、重开、重放的事件逐字段一致。若收益不足或内存、写入延迟显著回退，撤回该项改动。

## 取舍与风险

合并刷盘可望提高写入吞吐，但会形成崩溃时最近事件的丢失窗口，未被选择。把派生事件另写入 SQLite 会增加第二份持久化表示，也未被选择。主要实施风险是辅助索引漏更新、事件缓存与日志水位脱节，以及分块读取破坏 UTF-8 或残行处理；相应定向测试和缓存失配回退是验收条件。
