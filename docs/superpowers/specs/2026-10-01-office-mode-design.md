# 办公模式设计

## 目标与验收

用户在同一段 Agent 对话里创建并修改一份办公文档，同时看见对话和文档，能明确选择协作方式，并在失败后继续操作原文档。默认仍是 Agent 模式。办公模式首版提供 ONLYOFFICE 的文档、表格、演示和 PDF；WPS 只保留未来扩展位置，不作为可选功能。

验收分两阶段。前端演示阶段可完成模式选择、模拟发送、模拟文档与对话展示、设置项配置和当前窗口交互；所有模拟结果须清楚标记，不声称已创建真实文件或发起真实 Agent 请求。真实接口阶段须证明文档创建成功后才发起 Agent，请求失败不重复建文档，重试仍使用同一文档；工具和 Skill 限制在运行时生效，文档保存与重新打开可恢复。两阶段均不得改变普通 Agent 模式的既有流程。

## 已裁决的产品行为

- 新对话默认 Agent 模式。输入框按钮打开“办公模式 → 应用 → 文档类型”三级菜单。首版仅 ONLYOFFICE 可选，提供文档、表格、演示、PDF。首次发送前无右侧选择区。入口布局以用户给出的截图为参考。
- 一次对话只绑定一份文档。首次发送后应用与文档类型固定，输入框只提供协作／非协作切换。选择 ONLYOFFICE 时必须能在输入框选择并在后续对话中调整协作状态。
- 首次发送后才出现右侧文档和较窄的中间对话流；右侧文档比对话宽。复用既有嵌入浏览器。仅当前对话绑定的文档标签不可关闭，其他标签照常可关闭；UI 入口和浏览器命令均执行这一规则。
- 非协作模式下，Agent 生成期间当前 Action-Driver 窗口的人类编辑被禁止；生成结束、失败或中断后恢复。其他浏览器或设备上的编辑不在首版禁用范围内。协作修改在应用侧分别记录人和 Agent 的归属；独立协作者身份须另行验证，不把共用编辑会话误报为独立身份。
- 设置页为办公模式提供工具、Skill 多选。四种文档类型分别配置主提示词，没有办公模式通用提示词。设置的显示状态与真正执行权限分开处理，运行时按会话固定的选择进行工具发现和调用校验。

## 阶段一：插件化前端演示

扩展版本化、可序列化的插件 UI 贡献契约，使插件能声明会话模式入口和文档类型。宿主绘制输入框菜单、任务分栏和设置页，并通过依赖注入调用办公模式端口；ONLYOFFICE 插件提供选项、模拟行为和办公模式状态，宿主不写 ONLYOFFICE 专用业务分支。现有菜单贡献只支持插件菜单、任务工具栏和设置导航，不能表示输入框层级选择，因此需新增窄的会话模式贡献，而非把专用状态塞入现有菜单定义。

模拟服务在办公模式首次发送时生成本地演示用的会话与文档引用，随后展示模拟文档和模拟对话。演示态应在对话和文档区域可辨认；重试沿用同一个模拟引用，不伪造真实保存或 Agent 工具活动。前端状态模型包含应用、文档类型、协作状态、文档引用、演示／真实来源以及任务状态；应用与类型在首次发送后不可变。普通 Agent 模式继续走原有提交端口。

设置页通过注入端口读取可用工具和 Skill，保存四种文档类型的提示词及工具、Skill 选择。阶段一可以用可替换的模拟适配器演示读写，但须标明模拟设置不会限制真实 Agent。前端完成后用同一端口接入真实配置与执行，不再搬迁交互状态。

## 阶段二：真实文档与 Agent 接口

办公插件拥有“对话／会话 ↔ 文档”的绑定、创建编排和 ONLYOFFICE 适配。专用文档存储端口保存可变文件及版本，宿主任务记录只保留通用、可恢复的文档引用和浏览器保护所需的最小标识。现有插件私有存储仅处理 JSON，artifact 内联上限为 8 MB，不能直接承担持续编辑的 Office 文件主存储。绑定应有幂等键与明确的创建中、可用、失败状态，避免首次请求重试时生成第二份文件。

首轮发送按“固定类型与协作状态 → 创建并持久化文档绑定 → 打开嵌入页面并保护绑定标签 → 提交 Agent 请求”执行。创建失败时不提交 Agent 并给出可重试错误；Agent 失败时文档与绑定保留。继续对话时读取已有绑定并操作同一文档。ONLYOFFICE 的文档 `key`、版本与保存回调由插件适配层和存储端口协调，避免重开时误用新身份或丢失保存结果。用户关闭对话时按产品现有会话生命周期处理文档，不因页面隐藏而删除文件。

运行时从会话配置确定工具 grant、可加载的 Skill 和对应文档类型主提示词，在发现与直接调用两处校验。现有普通任务请求把 `skills` 固定为空且使用默认工具 grant，不能只靠设置页筛选。办公插件的 Skill 经受控能力端口调用 JS 写入接口；不得假设浏览器外部 Connector 在当前自建 ONLYOFFICE 版本可用。接口阶段先验证编辑器内插件脚本和自建服务之间的桥接，再固定可替换的写入端口与归属记录。JS 调用若共用人的编辑会话，应用审计记录须标识 Agent 操作，但界面不声称 ONLYOFFICE 原生协作者身份已经分离。

浏览器任务绑定层保存受保护标签的身份并拒绝所有关闭入口与 Agent 浏览器关闭命令；UI 同时隐藏或禁用该标签的关闭按钮。保护仅限当前绑定标签，不阻止其他标签关闭。非协作期间仅当前窗口以只读状态呈现人类编辑器；Agent 完成、失败和中断都恢复可编辑状态。此规则不保证其他窗口无并发修改，发生版本冲突时须保留文档并显示冲突，而非静默覆盖。

## Battle 结论、替代方案与权衡

本任务属于产品与架构混合的决策型任务。目标、两阶段成功标准及关键边界已由用户裁决。曾比较在宿主写 ONLYOFFICE 专用分支与扩展通用会话模式插件贡献：前者首版较快，后者让 WPS 可复用入口和状态边界；用户选择后者。曾比较由核心任务存储直接管理 Office 文件与由插件管理绑定、专用端口存储文件：前者调用链短，后者避免核心承担 Office 专有生命周期；用户选择后者。

前端先行时，推荐禁用真实发送直至接口完成；用户选择本地模拟文档与对话供演示。已知风险是演示与真实功能可能被混淆，因此必须显著标注模拟状态且不发真实 Agent。对于非协作禁编辑，推荐覆盖所有已打开的人类会话；用户选择仅限制当前窗口。已知风险是其他窗口可同时修改，真实接口须保留版本冲突处理。用户还裁决按文档类型分别配置提示词，不设通用提示词。已确认的默认 Agent、三级菜单、一对话一文档、标签保护、应用与类型锁定等不重复争论。

## 风险与验证

- ONLYOFFICE 编辑器内 JS 插件可写文档，但浏览器外部 Automation Connector 官方示例标注为 Developer 能力。先用自建版本做最小写入验证，再设计远端调用桥；若验证不成立，暂停接口实现并重新 Battle。参考 [编辑器插件 API](https://api.onlyoffice.com/docs/plugins/interacting-with-editors/overview/asc-plugin/) 和 [Connector 示例](https://api.onlyoffice.com/docs/docs-api/samples/automation-api/filling-out-the-form/)。
- ONLYOFFICE 保存依赖接入方回调，协作依赖稳定文档 `key`。接口测试须覆盖首次创建、回调保存、重新打开、失败重试与并发版本冲突。参考 [协作说明](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/co-editing/) 和 [保存回调](https://api.onlyoffice.com/docs/docs-api/usage-api/callback-handler/)。
- 嵌入网页由 Electron `WebContentsView` 承载，Renderer 弹层与原生视图层级可能冲突。前端阶段在无右侧、分栏、窄窗口、任务切换与标签保护状态下做真实界面检查。
- 定向测试覆盖插件贡献解析、模式状态锁定、模拟提交与重试、设置配置、浏览器关闭保护；接口阶段另覆盖创建顺序、运行时工具和 Skill 拒绝、保存与恢复、编辑状态归属。遵循仓库规定，迭代期不运行全量测试；提交前才执行一次全量验证。

## 范围外

首版不支持 WPS 实际接入、多文档对话、从已有文件导入、跨设备禁编辑，也不宣称 ONLYOFFICE 原生协作者身份已区分人和 Agent。阶段一不创建真实文件、不调用真实 Agent 或 ONLYOFFICE 服务。阶段二须在写入桥接验证后实施，不以模拟成功替代真实验收。
