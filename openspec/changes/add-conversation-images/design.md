## Context

参见 [proposal.md](./proposal.md)。目前 `ModelInputMessage`、`request.create`、`response.content`、任务投影和对话组件都只表示文字。Runtime 通过 OpenAI 兼容 Chat Completions 接入聊天模型，工具循环已有可取消的生命周期；模型连接和会话结构化记录在 SQLite，图片文件尚无独立存储。现有模型网关会记录请求/响应摘要，直接把图片 base64 加入模型请求对象会导致日志和 Phoenix trace 持有图片字节。

OpenAI 官方文档确认 Chat Completions 可用图片输入进行分析，而 Image API 的 generation endpoint 适合从文字生成图片；Responses API 还支持内置生图工具及多轮编辑。本次采用前两者的兼容协议，避免迁移现有聊天模型调用链。参考：[Images and vision](https://developers.openai.com/api/docs/guides/images-vision)、[Image generation](https://developers.openai.com/api/docs/guides/image-generation)。

## Goals / Non-Goals

**Goals:**

- 让用户上传图片提问，或让 Agent 用单独配置的模型生图，并在当前对话和历史会话中看到图片。
- 保持文本、工具、图片在同一请求内的持久化顺序；断线重连不重复生图。
- 所有图片及附件以会话 ID 区分目录；SQLite 继续负责结构化记录、事务和索引。
- 防止图片字节通过 WebSocket、事件、工具原始 I/O、模型调用日志或 Phoenix trace 泄漏和膨胀。

**Non-Goals:**

- 参考图编辑、局部重绘、遮罩、视频/音频，以及把图片作为 Markdown URL 自动抓取。
- 迁移 Responses API、支持任意供应商原生生图协议，或替换现有 SQLite 会话存储。

## Decisions

### 1. 视觉输入与图片生成使用独立路径

用户图片是聊天模型的多模态输入；生图注册为 `image_generate` 版本化工具，使用用户在模型列表指定的默认生图模型和 Images API 兼容适配器。工具 schema 接受 1 至 4 条图片需求，每条只包含 `prompt`；相同提示词可重复提交以生成多个变体，也可分别描述不同图片。Runtime 以最多 4 个独立 Images API 请求并行执行，不依赖提供方是否支持 `n` 参数；不让模型指定 URL、文件路径、凭据或提供方。没有已启用的默认生图模型时不向模型暴露工具。每个成功子请求都产生图片引用，失败子请求记录独立结果；完成后工具返回简短汇总，已生成图片作为本轮助手消息的有序内容块持久化。之后的模型续跑仍使用原聊天模型。

可执行替代方案是迁移到 Responses API 的内置 `image_generation` 工具。它有更强的多轮图片编辑与部分图片流，但当前模型接入以 Chat Completions 和兼容服务为中心，迁移会牵动模型连接、工具流和恢复协议。另一个替代是让聊天模型输出 Markdown 图片链接，再由 UI 渲染；它无法可靠管理生成模型、文件所有权和历史恢复。用户裁决采用独立工具与 Images API 兼容端点。

### 2. 图片作为有序消息块，传输只用引用

消息内容统一表示为有序 `text` / `image` 块；读取旧 `{text}` 记录时映射为一个文字块。输入、实时事件、快照和任务投影都传 `assetId`、MIME、尺寸、来源等元数据，不传字节。文字继续增量流式传输；并行生图中每张完成后，先持久化资产引用，再发布带请求序号的图片块事件，快照还原相同完成顺序。图片在助手最终消息中直接可见，工具行显示总数、已完成数与失败数。至少一张成功时工具可完成并附部分失败说明；全部失败时工具失败。取消整批时中止所有未完成请求，已持久化图片保留。纯图片消息合法。历史会话图片只在用户显式重新附加时再次作为模型视觉输入；首版不提供对已生成图片的自动编辑语义。

UI 通过已有本地服务的认证请求取得图片二进制，创建浏览器对象 URL 并在卸载时释放；缩略图、放大查看和保存复用同一资产。缺失文件只影响对应图片块，文字和其他块照常显示。不得依赖模型输出的任意 Markdown URL 把外部图片偷偷下载为本地资产。

### 3. 图片文件按会话目录存放，SQLite 保持事实索引

在应用数据目录使用 `sessions/<sessionId>/attachments/uploads/` 和 `sessions/<sessionId>/attachments/generated/`；实际文件名由 Runtime 生成随机 `assetId`，不使用用户原始文件名拼路径。SQLite 增加图片元数据、会话绑定、状态与消息引用。新会话尚未有 `sessionId` 时，上传先进入短期 `staging/`，`request.create` 被接受后绑定并原子迁入目标会话目录；失败与过期暂存文件可清理。已有会话直接绑定到对应目录。文件先写临时文件、验证完整性、原子改名，再提交引用与事件；提交失败留下的孤立文件可按索引清理。结构化消息、任务、事件及 LangGraph checkpoint 保持现有 SQLite 所有权。

认证上传接口接收有限大小的二进制请求，不经过现有默认 JSON body 记录路径；读取接口验证资产属于请求会话，仅提供已知 MIME，不暴露任意本地路径。首版接收 PNG、JPEG 和 WebP，限制数量、字节数及解码尺寸；文件扩展名以检测到的类型确定。实现时使用成熟的图片类型/尺寸读取库，不自行解析格式。

### 4. 连接复用凭据，能力配置独立

模型连接仍保存服务地址与加密凭据。现有模型列表的每行增加“图片输入”和“图片生成”能力开关；图片生成开关开启的行可被用户设为唯一默认生图模型。能力开关是用户声明，不根据模型名自动推断，也不在刷新 `/models` 列表时逐个发起可能计费的生图请求。现有发现/刷新功能仍负责列出模型，找不到的生图模型可手动添加；仅支持 Images API 的连接可保存模型而无需通过聊天补全测试，也不强制依赖 `/models` 端点。默认模型以现有 `ModelRef` 指向连接与模型，设置或切换它不改变会话聊天模型。关闭默认模型的生图开关、停用或删除其连接时清除默认引用。提供方真实兼容性在使用时判断，失败写入工具状态并提示可更换模型；图片输入能力也由用户声明，不支持视觉请求的提供方错误明确返回。原生 Anthropic 图像输入和其他供应商原生生成接口不属于首版。

### 5. 图片字节仅在调用边界短暂出现

模型网关和图像工具内部以资产引用工作。Chat Completions 适配器在真正发出视觉请求前读取图片并构造图片 content part；生成适配器接收提供方返回的图片数据或受支持的结果地址后立即验证并保存。模型请求、响应、工具原始 I/O 和遥测只记录模型 ID、资产 ID、MIME、尺寸、字节数、状态与耗时；对序列化请求体的现有日志路径做显式媒体脱敏。运行中取消经 `AbortSignal` 传到图像调用，若提供方已完成但取消先被确认，不再把迟到结果作为成功图片广播。

## Risks / Trade-offs

- [手动能力开关可能开启了不兼容模型] → 不把开关等同验证结果；实际调用失败时给出明确原因，保持设置可修改。用户裁决不做自动筛选和批量能力探测。
- [4 张并行生成可能遇到限流或多笔费用] → 工具 schema 限制最多 4 条需求，逐张显示完成与失败，取消时停止未完成请求；不暗示并行调用能保证提供方吞吐。
- [图片上传时尚无会话 ID] → 暂存目录采用短期租约和绑定状态，超时清理；不把暂存路径写进正式消息。
- [文件与 SQLite 无跨介质原子事务] → 先落文件再提交引用，启动或定期清理孤立文件；引用存在而文件缺失时展示占位，不破坏整轮恢复。
- [多模态上下文和费用增加] → 上传数量、尺寸和字节数有界；界面在发送前显示附件，能力不支持时阻止提交并保留草稿。
- [OpenAI 兼容服务的生图进度不统一] → 首版保证准备、运行和最终图片状态；部分图片预览不是验收条件。
- [历史与旧消息格式] → 读取器兼容旧文字记录；数据库迁移和回滚保留备份，旧任务无需重写为图片块。
- [用户覆盖] → 用户要求直接在模型配置列表设能力开关和默认模型，覆盖了先前的“自动搜索候选并在选中后验证”建议；已知代价是开关无法证明端点真实兼容，错误可能直到首次生图才显现。首版只覆盖 Images API 兼容端点，其他供应商接口与编辑能力延后。

## Migration Plan

1. 扩展 SQLite schema，保存资产元数据、模型图片能力和默认生图模型；迁移前按现有规则备份数据库。
2. 引入会话附件目录和资产服务，再扩展消息内容、流协议与任务投影；旧文字记录在读取端保持兼容。
3. 接入视觉适配、生图工具和设置 UI；最后接入输入框和图片展示，避免出现无法读取的图片引用。
4. 验证旧任务、上传识别、生图、断线恢复、取消、文件缺失和打包后的实际路径。回滚时保留新增附件目录及数据库备份，不删除用户图片。
