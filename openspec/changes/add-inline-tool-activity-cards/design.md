## Context

当前 `TaskPage` 只在对话视口外渲染等待批准的 `ToolApprovalBar`，`StreamTaskProjection` 则将工具事件压缩为不含终态输出和耗时的 `ToolInvocationProjection`。现有工具生命周期与聚合日志已经有稳定 call id、顺序和批准状态；本设计复用这些边界，而不把执行日志拼进模型正文。动机见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 让所有 Runtime 工具以同一张内联卡跨越批准、执行和终态。
- 区分默认展开的运行区与默认折叠的完成区，并在重连/重开任务时可恢复。
- 只将既有安全边界允许的受限摘要投影到 Renderer。

**Non-Goals:**

- 不改变工具批准策略、模型循环、工具执行顺序或交互日志的数据保留策略。
- 不在对话中显示原始 stdout/stderr、HTTP 载荷、密钥、Cookie 或任意完整结果。
- 不为某一个工具类型增加专用卡片，亦不在本变更实现 Browser/Computer 的独立时间线。

## Decisions

### 1. 以调用卡为唯一 UI 实体，而非为每个事件追加一行

Renderer 按 call id 维护单一活动投影；状态事件更新同一卡片。运行区过滤非终态调用，完成区过滤终态调用，保留 Runtime 已定义的确定顺序。最新运行卡默认展开，卡片一旦终态即迁移到完成区并恢复为折叠。

备选方案是在消息流直接追加“正在读取”“读取完成”等纯文本事件。它实现快，但会污染正文、重连时重复且无法容纳批准操作。最终裁决采用单一卡片。

### 2. 新增专用、安全的活动展示投影

Runtime/共享 contract 为活动卡传递受限摘要、顺序、起止时间或耗时及终态受限输出。投影在 Runtime 边界从聚合结果构造；Renderer 不解析原始 ToolEvent、日志详情或 transport 载荷。

备选方案是让 Renderer 通过日志 API 拉取完整工具记录。该方案增加时序耦合，并可能让本不适合对话展示的数据跨越日志边界。最终裁决采用独立受限投影。

### 3. 将批准控件嵌入等待状态卡

`waiting_approval` 卡使用现有 task/call/argumentsHash 的一次性批准命令，调用成功后禁用重复提交；拒绝和错误仍更新同一卡片。现有单独的 ApprovalBar 被活动区替代而非同时保留。

备选方案是保留底部 ApprovalBar 并另做只读卡片。它会使同一次调用在两个位置出现，用户难以判断操作对象。最终裁决采用卡片内批准。

### 4. 只给有可见子项的任务组提供展开入口

任务组过滤模型正文后，只有包含工具项才有可展开内容。空组显示静态标题，不使用可聚焦的折叠控件或箭头。有工具项的组保持整行可点击和键盘可操作；箭头在鼠标悬停或键盘聚焦时显示，触屏设备保持可见。

备选方案是有内容时常显箭头。它更容易被发现，但增加运行中任务组的视觉噪声。用户裁决采用按交互状态显示箭头；主要风险是触屏和键盘缺少悬停，故为这两类输入保留箭头可见性。

### 5. 正文切分连续工具组，标题由 Runtime 确定

每个非空正文片段开始时结束当前工具组；后续工具调用创建新组。没有正文隔开的工具调用沿用同组，单个工具也有独立组。组内只放工具，不放模型正文。等待模型且没有正文或工具在运行时，Renderer 显示瞬时“正在思考”状态行。完成后先前正文和工具组一起归档，最后一段模型回复保持展开。

工具行标题由 Runtime 根据工具类型、受限参数摘要及生命周期构造。单工具组标题描述该工具动作；多个同类工具按数量概括；混合工具按操作数量概括。组图标运行时跟随当前工具，完成后同类保留类型图标、混合类型使用通用工具图标。运行中的组标题和工具标题使用低强度扫光，终态停止，并遵循 reduced-motion。

备选方案一是为每次工具调用额外请求 LLM 起标题，会增加延迟与成本，且失败时标题晚于工具事件。备选方案二是要求模型在工具调用中附带标题，当前 ModelResult 契约不支持，模型也可能遗漏或输出不合适内容。用户裁决采用 Runtime 规则，不增加模型标题调用。

### Battle 结论

- 类型：产品 / 架构混合
- 目标：让用户在对话附近区分正在发生与已结束的工具操作。
- 当前方案：所有 Runtime 工具使用两区、可折叠的 Codex 风格活动卡。
- 主要质疑：把工具过程混入 Assistant Markdown 会破坏正文边界并放大敏感输出面。
- 替代方案：仅 Web Search 卡片，或仅在日志页显示详情。
- 最终决策：所有 Runtime 工具统一卡片；运行区默认展开最新步骤，完成区默认折叠。
- 主要权衡：需要扩展跨进程安全投影与恢复测试，以换取一致的可见性。
- 用户覆盖：无。
- 后续交互裁决：用户选择任务组箭头仅在悬停或键盘聚焦时显示，并在触屏保持可见；空组不可展开。已比较有内容时常显箭头的方案。
- 后续范围澄清：同一规则适用于活动区内全部展开箭头，包括耗时归档、任务组和工具输入/输出；没有可展开内容的行不提供箭头或展开控件。
- 后续交互裁决：正文片段强制分隔工具组，单工具也成组；工具与组标题采用 Runtime 确定性规则，不由 LLM 生成；组图标随工具类型变化。
- 重新开启条件：需要展示完整原始输出、引入工具专属页面或改变日志保留边界。

## Risks / Trade-offs

- [实时事件乱序或重连重复] → 按既有 call sequence 去重并以快照校准，卡片不得依据到达顺序重复创建。
- [摘要在对话区泄漏秘密或过长] → Runtime 白名单字段、固定长度上限，Renderer 只渲染该投影。
- [多卡片挤占窄布局] → 运行区只自动展开最新一项，完成区默认折叠并使用现有对话流宽度。
- [终态时间缺失] → 将缺失时间呈现为无耗时信息，不推断或伪造耗时。
- [箭头按悬停显示时触屏与键盘不易发现入口] → 聚焦时显示箭头，触屏保持箭头可见；空组不提供虚假入口。

## Migration Plan

1. 扩展 contracts、Runtime 事件与快照的安全活动投影，保留既有工具和日志行为。
2. 让 Renderer 投影、活动区和批准控件使用该投影，并移除重复的独立批准栏。
3. 用单元、流式重连和真实桌面 E2E 覆盖生命周期迁移；回滚时停止渲染活动区，Runtime 仍保持原有工具事件与日志。
