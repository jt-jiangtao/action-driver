## Context

仓库当前通过 OpenSpec 记录产品与架构决策，并在设计文档中使用 `Decisions` 和 `Risks / Trade-offs`，但没有根级 Agent 指令，也没有统一的 Battle 分类、结束条件或用户覆盖规则。治理规范必须同时对不同开发 Agent 可发现、对 OpenSpec 工作流可执行，并避免将运行时 Agent 的 Skill 契约与开发流程治理混为一谈。

## Goals / Non-Goals

**Goals:**

- 为所有开发 Agent 提供简短、强制且优先级清晰的入口规则。
- 将已有产品 Battle 的核心方式扩展到产品与架构决策。
- 用两级分类避免低风险执行任务被无意义讨论阻塞。
- 让 Battle 结论进入 OpenSpec，形成可以回溯的决策链。
- 定义用户覆盖 Agent 建议后的停止条件，避免无休止争论。

**Non-Goals:**

- 不改变 ActionDriver 产品运行时 Agent Loop 或 Skill Contract。
- 不要求每次代码编辑都生成独立 ADR 或 OpenSpec。
- 不建立自动评分、投票或审批系统。
- 不允许 Agent 以 Battle 为由否定用户对项目的最终决策权。

## Decisions

### 采用“两级 Battle”而不是所有任务强制辩论

决策型任务强制 Battle，执行型任务直接推进并保留升级机制。这样既能阻止未经审查的重大决定进入实现，也能避免简单修复出现表演式反对。

备选方案是所有任务无条件 Battle。该方案规则简单，但会显著增加机械任务成本，并激励 Agent 为满足格式虚构分歧，因此不采用。

### 使用三层文档结构

1. 根目录 `AGENTS.md` 保存不可跳过的分类、门禁和优先级规则，确保 Agent 在进入项目时立即读取。
2. `docs/governance/agent-battle-protocol.md` 保存完整检查维度、对话格式、结束条件和示例，避免根指令过长。
3. `openspec/config.yaml` 为 proposal、design 和 tasks 增加与 Battle 结论一致的产物规则，使规划产物成为决策记录。

备选方案是只更新 OpenSpec 配置。它无法约束不经过 OpenSpec 的仓库工作，也无法为 Agent 提供完整协议，因此不采用。

### 产品 Battle 与架构 Battle 共用流程但使用不同检查表

两类 Battle 都遵循“目标 → 假设 → 证据/反例 → 替代方案 → 权衡 → 推荐 → 裁决 → 记录”，但产品侧重点是用户与价值，架构侧重点是边界、耦合和演进。这样保留统一心智模型，同时避免用技术指标替代产品判断。

### 用户拥有最终裁决权，但覆盖必须显式记录

Agent 必须基于逻辑和最佳实践提出真实异议；用户理解风险后仍可覆盖建议。覆盖发生后，Agent 记录风险并停止重复争论，除非出现新证据。该规则平衡专业挑战与项目所有权。

### 只读探索不受实施门禁限制

Agent 可以在 Battle 前读取代码、规范、历史决策和运行诊断，因为没有证据就无法进行高质量质疑。创建文件、修改设计、安装依赖、执行外部写操作和实现功能属于门禁后的工作。

## Risks / Trade-offs

- [任务分类可能被 Agent 用来规避 Battle] → 在协议中列出明确的决策型触发项，并规定发现隐藏决策时必须升级。
- [Battle 退化为固定模板] → 要求每个异议关联当前目标、证据或具体失败模式；没有实质异议时必须如实说明。
- [用户与 Agent 反复争论] → 定义明确结束条件和用户覆盖机制；没有新证据不得重复开启同一争点。
- [OpenSpec 文档重复对话内容] → 仅记录最终决策、替代方案和关键权衡，不保存完整聊天逐字稿。
- [根级指令过长降低可执行性] → `AGENTS.md` 只保存强制规则，将解释、模板和示例下沉到治理文档。

## Migration Plan

1. 新增根级 `AGENTS.md`，引用治理协议并声明其适用范围。
2. 新增完整 Battle 协议与产品、架构检查表。
3. 更新 OpenSpec 配置，为规划产物增加决策留痕约束。
4. 使用当前变更作为首个合规样例，验证分类、Battle 结论和 OpenSpec 记录一致。
5. 若规则造成不可接受的流程阻塞，可回滚配置规则与治理文件；产品运行时不受影响。
