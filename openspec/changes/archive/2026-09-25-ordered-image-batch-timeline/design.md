## Context

参见 [proposal.md](./proposal.md) 和 [已确认的书面设计](../../../docs/superpowers/specs/2026-09-25-ordered-image-batches-design.md)。目前 `AgentResponse` 先渲染完整文字再渲染整个画廊；消息归一化、Runtime 终态与桌面流投影均把文字重排到图片前。图片资产首次完成才进入助手消息，因此单靠图片顺序不能表示调用开始的位置。AgentGraph 当前顺序执行工具调用，但显示契约不能依赖资产完成顺序。

## Goals / Non-Goals

**Goals:**

- 在调用开始时建立可持久化的批次位置，让实时、重放、快照和历史使用同一有序消息结构。
- 批次按调用顺序、批内按输入索引；完成、失败、取消只更新固定插槽。
- 最终回复文字位于其生成位置；已归档的过程文字不重新常显。

**Non-Goals:**

- 不修改生图提供方接口、每调用的并发限制、图片文件存储和用户上传图片气泡。
- 不猜测旧记录此前被归一化丢掉的原始时序，也不使过程文字常显。

## Decisions

### 以消息部件保存批次锚点

在 `MessageContentPart` 增加 `kind: 'image-batch'`，保存调用 ID 和图片数量。Runtime 看到 `image.generate` 进入运行态时，在当前助手内容尾部插入锚点，并使用已有“保存助手消息及事件”的事务能力写入新的 `response.image_batch` 事件。事件含调用 ID、数量和内容位置，不含图片字节与提示词。对应图片继续使用现有 `kind: 'image'` 和 `generation.callId/index`。批次锚点一旦建立就不因工具终态、图片乱序完成或最终文本生成而移动。

选择独立锚点而不在工具数组中推断画廊位置，是因为工具数组没有文字边界；选择新增明确事件而不依赖 `tool.running` 在前端自行合成，是为了让持久化消息、回放事件和快照共享同一事实来源。用户已裁决采用调用顺序穿插；真实替代方案“把所有图片统一置顶”只需较小的渲染改动，但无法表达批次之间的文字，因此不采用。

### 保留内容顺序的归一化

`normalizeAssistantParts` 只合并相邻文字，按 `(callId,index)` 去重图片并按 `callId` 去重锚点；它不跨锚点合并文字，不按图片完成时间重排不同批次。桌面投影按批次事件插入锚点，按图片事件更新对应资产，并以事件 `contentIndex` 定位文字片段。终态使用模型的最终内容校准最终文字片段，移除前几轮已进入活动归档的过程文字，不移动锚点和图片。旧记录没有锚点时保留已存 `parts` 的顺序；无法从旧数据还原的顺序不做迁移。

### 按锚点渲染独立画廊

`AgentResponse` 顺序遍历助手部件：文字交给 Markdown 渲染；每个批次锚点交给对应 `callId` 的画廊；该批全部插槽按 `imageCount` 和原始索引创建。无锚点的旧生成图片以记录顺序显示在兜底画廊。`ImageGallery` 只负责单批插槽和状态，不能再次按全部工具或资产顺序合并批次。这样后续批次的结果先完成时也只能填自己的位置。

## Risks / Trade-offs

- [协议与持久化同步] → 同时修改共享类型、Zod 流协议、Runtime 发布与桌面投影，并用端到端事件顺序测试校验；批次消息及事件写入使用单一事务。
- [终态文字重建仍可能移动内容] → 仅校准最终文字片段，保持锚点和资产原位；分别测试终态、取消、失败与恢复。
- [旧记录缺少锚点] → 保留持久化顺序作为可验证的兼容行为，不伪造已丢失的调用时序。
- [请求内工具目前顺序执行] → 以调用事件作为位置来源，不以当前执行策略作为长期契约；测试模拟后一批资产先到达。
- 用户覆盖 Agent 建议：无。

## Migration Plan

不更改 SQLite 表结构。新增的消息部件和事件类型按新协议写入；读端同时接受旧文字、旧图片部件与新锚点。若回滚应用版本，应回滚到写入新类型前的数据库备份，因为旧版流协议不能解析新增事件；正常升级不重写历史消息。
