## Context

见 proposal.md。Runtime 的 `capabilityCandidates` 已固定前三项，但仅对目录标记的生图模型及未知模型附加 `image_generation`。`probeCapability` 已能按连接地址选择 Token Plan 或 Images API，实际生成一张图并校验图片。桌面模型选择投影目前只传递模型名称和视觉布尔值，下拉行没有四项测试数据。

## Goals / Non-Goals

**Goals:**

- 单项、向导批量和刷新测试沿用一份固定四项候选清单，四项并行、每批最多四模型并发。
- 模型选择器直接使用已有的逐项结果，无额外请求，显示四项的可读状态。
- 保留聊天候选资格与能力探测结果的独立判断。

**Non-Goals:**

- 不新增音频和视频专项测试，不改变生图接口选择及默认生图资格。
- 不在模型选择器展示提供方错误详情或阻止未测试、失败的聊天候选被选中。

## Decisions

1. **所有模型都实际生成一张测试图。** `capabilityCandidates` 固定返回文本、推理、视觉、生图四项，不用模型名称、目录或历史结果筛选生图。现有 `probeCapability` 与提供方适配器负责图片验证和失败归类。替代方案是仅手动测试生图，能减少费用，但无法满足刷新后所有模型具备生图实测状态。用户明确选择全量真实测试并接受可能费用、限流和较长耗时。
2. **能力状态投影到下拉行。** `ModelSelectionProjection` 为可选择的聊天模型携带四项展示状态，由已存 `capabilities` 派生：`success` 为成功，`failed`、`unsupported`、`inconclusive` 为失败，缺项为待测试。信息图标紧跟模型名称，选中对号单独靠右；仅在悬停图标或键盘导航行时显示简短浮层，供屏幕阅读器读取同样内容。替代方案是始终展示四个标签，会挤占模型名称，且与用户此前要求的选择界面保持简洁相冲突。用户明确选择逐项状态，而非只列成功能力。
3. **探测和聊天用途继续分离。** `chatCandidate` 不从四项探测候选推出；纯生图及已知音视频模型不因新生图测试进入聊天列表。无测试结果的已启用聊天候选仍可选。默认生图仍仅接受生图实测成功的模型。

## Risks / Trade-offs

- [所有模型均发送真实生图请求，可能计费、触发限流或因提供方不支持而失败] → 用户已明确覆盖按目录筛选的方案；保留最多四模型并发、现有超时和失败隔离。每模型只生成一张测试图，不写入会话。
- [Token Plan 生图请求最长 120 秒，批量完成可能较慢] → 所有模型同时显示测试中，各模型独立完成；保持既有单项重试能力。
- [旧连接缺少逐项结果] → 浮层显示待测试，不把目录推断为成功；测试后使用持久化结果更新，无数据迁移。
- [浮层遮挡下拉项或鼠标离开即消失] → 靠近信息图标定位，保持简短，并通过键盘导航和屏幕阅读器提供同等信息。

## Migration Plan

无需数据库迁移。升级后旧模型立刻显示四项候选，缺失项为待测试；用户刷新或单项测试时生成新的结果。回滚代码可恢复旧生图候选策略，已保存的逐项测试结果仍可读取。
