## Context

见 `proposal.md`。当前 `capabilityCandidates` 同时决定探测集合与聊天候选判断：Token Plan 目录会跳过部分三项测试，未知模型也不测推理。设置页按该集合生成状态标签，刷新只测试非空集合的模型。`/models` 发现结果只有模型 ID，没有可靠的能力元数据。

## Goals / Non-Goals

**Goals:**

- 对每个模型都并行运行文本、推理、视觉三项探测，三项不从模型 ID、目录声明、旧类型或历史测试结果推断。
- 保留现有可选生图探测、最多四模型并发、逐项二态 UI、内部诊断信息与默认生图资格。
- 新的统一探测集合不得让已知纯生图或音视频模型误入聊天选择器。

**Non-Goals:**

- 不新增音频、视频专项能力测试，不接入尚不支持的聊天协议。
- 不把测试失败等同于模型永久不可用，也不改变会话发送后的错误展示。

## Decisions

1. **三项固定测试，生图测试单独判断。** Runtime 为每个模型固定返回 `text`、`reasoning`、`vision` 三个探测候选；现有生图候选继续附加在后。向导、刷新与单项测试使用同一集合，现有并行探测器分别记录结果。替代方案是仅对目录标记的聊天模型测三项；请求更少，但用户明确拒绝了依名称跳过测试。最终裁决为所有模型测三项。
2. **测试覆盖率与聊天用途解耦。** `probeCandidates` 只表达要测试什么；单独的可选 DTO 标志表达现有聊天候选规则。Runtime 聊天路径也使用同一用途判断，防止设置页显示和实际发送冲突。已知纯生图、语音、视频模型继续不进入聊天下拉列表；未知模型保留为可尝试聊天候选，调用错误仍在对话展示。目录仅用于用途筛选与现有生图探测，绝不决定三项探测是否执行。替代方案是以文本探测成功判定聊天用途；这会阻止未测试聊天模型发送，违背已确认的交互规则。
3. **状态逐项呈现。** 三项在所有模型行均显示待测试、测试中及最终成功或失败；音视频专项标签继续隐藏。即使图片或音视频模型的三项均失败，模型行与生图成功结果仍保留。请求级失败把本轮三项都标为失败，避免显示旧成功。
4. **批量开始即标记全部待测行。** Renderer 在发现模型后一次标记全部待测模型为测试中，再用四个工作者排队发送请求。每行完成后单独清除其测试中状态；批次异常或结束时清理残余状态。测试中表示本批已排队或正在请求，不表示该模型请求已经发出。

## Risks / Trade-offs

- [纯生图和音视频模型接收额外聊天请求，可能产生计费、限流或预期失败] → 用户已明确覆盖仅聊天模型测试的推荐方案；保留四模型并发上限及每项超时，失败独立记录。
- [部分提供方不返回可验证的推理字段，出现“推理失败”] → 沿用严格的实证判定，内部保存真实响应错误；设置页仍按已批准的二态规则展示。
- [目录用途分类可能落后于实际提供方能力] → 它只影响聊天下拉列表与生图入口，不再抑制三项探测；未知模型可实际发送，提供方错误进入对话。

## Migration Plan

无数据库迁移。部署后当前候选清单会立即显示三项；历史结果保留已验证项，缺失项显示待测试。用户单项测试或刷新即可得到三项本轮结果。回滚代码即可恢复原探测候选规则，已有测试记录仍可读取。
