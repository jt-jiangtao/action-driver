## Context

设置页已有模型发现和逐模型能力测试接口。当前刷新只调用发现接口；测试运行态只写入 `testState`，而模型行从能力结果判断运行态。异常没有在行内呈现。参见 proposal.md。

## Goals / Non-Goals

**Goals:** 一次刷新完成发现和所有可测试模型的探测；进度与错误在原位可见；列表操作清楚且紧凑。

**Non-Goals:** 不新增音视频探测，不改变能力探测协议、持久化格式或模型调用接口。

## Decisions

1. **刷新即发现并测试。** 用户已裁决刷新时自动测试全部。替代方案是保留只发现的刷新并另设“测试全部”；它能避免意外的付费生图请求，但不能满足用户的一键操作。按钮文案明确写为“刷新并测试”，并提示生图测试可能产生费用。
2. **在设置页协调批次，复用现有服务。** 先调用 `refresh`，再按发现的可测试模型逐个调用 `testConnectionModels`。逐个调用可显示逐行进度、隔离单模型异常并避免并发打满服务商限流。替代方案是在 Runtime 增加批量端点；这会扩展跨进程协议而当前接口已足够。
3. **瞬时状态与持久结果分开。** 设置页记录正在测试的模型、批次进度及请求级错误；能力结果仍以服务端查询为准。每个模型完成后刷新查询，失败时显示原始错误摘要并允许重试。使用运行中集合与 `testState` 作为运行态来源，避免能力对象尚未更新时继续显示“待测试”。批次与单项测试互斥，并用同步锁阻止同一事件周期内的重复请求。
4. **紧凑行布局。** 模型名与能力结果为主信息，测试、启用和符合条件的默认生图操作在右侧对齐。无资格模型不渲染空占位。原四列表格的空列与大面积留白会放大视觉噪声。

## Risks / Trade-offs

- [刷新触发真实生图并可能收费] → 按用户裁决执行；按钮文字和说明明确后果，不对音视频模型发请求。
- [顺序测试多个模型耗时较长] → 展示完成数、当前模型和逐行状态；单项失败后继续，重复点击不启动第二批。
- [发现成功但部分测试异常] → 保存已完成结果，行内显示请求错误，批次继续；下次可单独重试。

## Migration Plan

不迁移数据。更改仅在设置页协调和呈现。回滚界面代码即可恢复原刷新行为。
