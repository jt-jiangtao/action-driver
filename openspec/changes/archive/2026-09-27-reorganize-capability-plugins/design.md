## Context

已存在统一插件平台。现有资源复制及 Skill 工具注册仍绕过平台，见 proposal。用户已明确确认能力分组并要求开始实施。

## Goals / Non-Goals

完整资源同包、纯 catalog、按插件启停、原工具与安全契约兼容。保留数据库、Skill 文件归属、沙箱、凭据和产物事实在宿主；不增加新的文档工具、不修改 browser fork。

## Decisions

1. 四类文档独立插件，只发布各自 Skill 与已有脚本资源；替代统一 skills 大包被用户明确否决。skills 只拥有 Skill 管理/创作，imagegen Skill 归 image-generation。
2. web 包内 search/reader 分模块。替代保持独立包会继续分裂同类能力；用户选择合并。没有搜索 endpoint 时仅注册 web.open。
3. Skill 工具业务编排迁入 skills 公共 SDK 模块，宿主注入只读/安装/工作区校验窄接口。替代把 AgentFileStore/授权数据库一起迁入插件改变事实归属，因此继续保留内核安全端口。
4. 插件 catalog 以生成的静态元数据和完整相对资源索引描述 Skill；内容直接 import 包内文件，其他指令文本同样使用文件 import，构建时通过 text loader 打包；实际资源原样复制，脚本不伪造新工具。构建归集所有插件并清除过时构建包。既有内置 Skill ID 继续保留，生产初始化跳过传统副本。
5. 合并 web 后旧内置包不自动加载；保留私有数据；没有在途旧进程的启动阶段应用归属迁移。新包版本递增，避免不可变缓存复用旧代码。

检查范围、单一职责、资源完整、权限及配置兼容，无新增实质性异议。用户已裁决；先前设计中的传统 Skill 保留策略在本次范围内被更新。

## Risks / Trade-offs

- [读取脚本路径变化] → 完整资源随包，Skill 宿主返回实际受管理路径，command 沙箱继续只读允许 Skill 根目录。
- [陈旧 system/安装目录造成重复] → 保留个人资源，只移除受管理副本；停用旧归属、清理构建陈旧目录，私有数据保留。
- [资源索引与内容漂移] → 直接文件导入、资源索引生成器、完整文件比对与真实插件集成回归。
- [图像/Skill 授权绕过] → 由运行时权威上下文与原 grants 校验端口。

## Migration Plan

先建立归属与资源完整测试，再迁资源/合并 web、迁 Skill 工具与宿主接口，最后更新 Runtime、构建、E2E 和说明。回退通过代码版本保留，个人 Skill 与私有数据不删除。按仓库规定迭代只定向测试，准备提交时才跑一次全量。
