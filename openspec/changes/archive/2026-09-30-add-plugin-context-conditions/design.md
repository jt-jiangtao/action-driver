## Context

见 `proposal.md`。当前 `PluginManager` 原子发布与回收贡献，`RuntimeToolRegistry` 保存已注册工具，`agent-graph` 构造模型发现集合，`tool-invocation-service` 解析直接调用。`commands.execute` 经 `CapabilityRouter` 调用插件。现有 Desktop 菜单不属于插件贡献；并行变更负责其新结构。

## Goals / Non-Goals

**Goals:** 条件语义可在进程边界传递、共享求值、随键更新，并在发现与执行两处生效；插件实例键由宿主回收。

**Non-Goals:** 不复制 VS Code 的完整表达式语言，不定义菜单或视图贡献结构，不把条件当作授权，不使插件得到任务数据库或任意 Electron 状态。

## Decisions

### 1. 宿主持有键和纯求值器

在公共契约中定义键、值与条件语法，Runtime 持有当前快照。插件通过受限 SDK/RPC 更新自身前缀的键；宿主键由明确的内部端口设置。每次修改生成单调版本并通知消费者。解析在清单校验时完成，求值不执行代码。未知引用使整个表达式为 false，防止 `!unknown` 意外开放。表达式设固定复杂度上限，避免高频更新时的资源耗尽。

替代方案是每个入口向插件请求布尔回调：局部实现简单，但跨进程同步、崩溃时状态和一致诊断均更难，故不采用。用户已确认宿主键方案。

### 2. 生命周期与条件分开

贡献仍按现有激活事务发布，条件改变只更新投影，避免反复启停插件。插件停用或实例失效时按 `PluginOwner` 清理其键；旧实例更新由现有 epoch 校验拒绝。条件附于贡献声明但不修改 handler 注册形态。菜单和视图贡献由 `extend-declarative-plugin-contributions` 定义，并调用本变更的纯求值接口。

首版仅命令和工具的完整发现/调用路径接受 `when`。Skill 等尚未接入的贡献声明该字段时安装失败，防止有效清单实际无条件发布；并行菜单/视图变更在接入相同检查后再扩展可声明类型。

替代方案是条件变假即注销、变真即重新注册贡献：会扰动注册冲突、在途调用和模型名所有权，故不采用。并行变更边界已获用户确认。

本变更交付通用求值与版本通知；并行变更目前仍在规划阶段，其可见菜单和视图接入及集成测试由该变更实施。

### 3. 发现与执行双重检查

Runtime 在模型工具发现及命令可用性投影时求值，在 `tool-invocation-service`、`agent-graph` 工具执行入口以及 `PluginManager.invoke` 的命令路径重检。条件失败返回可诊断的不可用错误；随后仍走现有 grants、输入与能力路由检查。检查与调用开始之间的快照作为本次调用判定点；之后的状态变化只影响新调用。

替代方案是只筛选界面和模型列表：可被直接调用绕过，故不采用。

## Risks / Trade-offs

- [并行变更同时修改贡献契约] → 本变更只增加通用可选条件与求值接口；实施前核对 `extend-declarative-plugin-contributions` 的最新字段，避免覆盖其改动。
- [插件错误条件隐藏能力] → 安装时校验、提供位置诊断、未知键安全失败；不保存不可解释的回调状态。
- [条件与授权被混淆] → 文档和测试明确两门独立，直接调用必须同时通过。
- [高频键更新增加发现成本] → 版本化快照与依赖键索引；设置表达式规模上限。
- [首版语法有限] → 使用稳定受限子集，新增运算符须另行裁决；用户未覆盖此风险。

## Migration Plan

旧清单不含条件时等价于恒真。新增公共字段保持向后兼容；脚手架展示可选用法。先接入解析与 SDK/RPC，再接入注册和发现/调用；定向测试通过后才迁移少量内置配置门控。回退时旧清单仍可读取，撤销新条件声明即可恢复旧行为；不迁移持久化任务或 grants。
