## Context

见 [proposal.md](proposal.md)。现有任务输入和生成产物有稳定标识、会话归属及安全打开规则；插件 Host API 也有资源句柄，但没有通用的本地/远程资源 provider。统一 URI 必须保留这些权威记录，不能把文件路径或 URI 字符串升级为权限凭据。

## Goals / Non-Goals

**Goals:**

- 通过同一抽象路由本地与远程资源的读取、写入、列举和监听。
- 保留输入原件和已交付产物的不可变性、历史版本及会话隔离。
- 断连、冲突、取消和 provider 卸载产生可辨识结果。

**Non-Goals:**

- 不允许网页或插件取得任意本机文件系统访问权。
- 不把远程资源自动下载到本地，亦不改变旧任务文件标识的含义。

## Decisions

### URI 只负责定位，授权由宿主重算

定义版本化资源引用，携带 scheme、稳定资源 ID 和可验证作用域；provider 注册表解析 URI，操作时以宿主的权威任务/会话身份执行权限检查。旧文件 ID 通过兼容映射指向对应 URI，历史记录无需批量改写。替代方案是签名 URI 充当长期访问令牌；它在复制、日志泄露和权限撤销时风险更大，不采用。

### Provider 协议覆盖完整文件操作

统一 read、write、list、watch 的元数据、版本条件、流式内容、取消和错误码；本地输入、产物、插件资源与远程资源由不同 provider 实现。写入采用预期版本防止覆盖，监听包含可重新同步的序号或失效提示。替代方案是先做只读打开代理，成本更低但不满足用户裁决的完整平台能力；用户已明确选择完整协议并接受迁移成本。

### 只读现有资源与可写工作资源分开

输入原件和登记产物的 URI 是只读的；编辑或派生内容写入可写工作资源并获得新版本/标识，成功交付后再按既有任务流程登记。这样统一写 API 不会破坏旧任务指向的副本。替代方案是对所有 URI 提供原位写入，会破坏现有不可变版本规范。

## Risks / Trade-offs

- [完整 provider 协议跨 Runtime、Desktop、插件和远程传输，成本显著高于只读统一入口] → 分层契约测试、版本迁移和独立 provider 验收；这是用户覆盖小首版建议时接受的代价。
- [URI 被误当授权令牌] → 每次操作重新校验权威上下文，拒绝跨会话读、列举和监听。
- [远程写入中断留下半成品] → 版本条件和提交边界，未知结果必须可查询或人工处理，不能默认为成功。
- [监听断线遗漏事件] → 使用版本/序号检测缺口并要求重新同步。
- [旧历史数据无法解析] → 保留旧 ID 映射直到完成兼容验证，不静默回退到同名路径。

## Migration Plan

1. 定义 URI、provider、授权上下文、错误与版本协议，并对旧 ID 提供只读兼容解析。
2. 接入输入与产物 provider，验证跨会话隔离和历史副本。
3. 接入可写本地/插件资源与远程 provider，完成读写、列举、监听、取消及断连测试。
4. 将 Desktop 打开和插件资源 API 切到统一入口；保留旧入口作兼容适配，验证后再移除。回滚时旧 ID 与既有文件记录继续有效。
