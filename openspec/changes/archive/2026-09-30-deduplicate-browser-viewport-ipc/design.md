## Context

见 `proposal.md` 的探针与动机。`BrowserPanel` 的单个 effect 在挂载、`ResizeObserver`、窗口 `resize` 和清理时调用同一个 `update`；preload 对每次调用执行 IPC，manager 再做可信发送方及任务归属校验。上一轮宿主去重不影响这些上游调用。effect 依赖 `mode`，因此分栏与放大切换会先发送隐藏、再发送可见状态。

## Goals / Non-Goals

**Goals:**

- 单个 effect 生命周期内只跳过和最近一次请求具有相同 task、session、四个取整边界及可见性的请求。
- 初次可见请求、变化的边界、布局切换的隐藏／恢复及卸载隐藏均即时发送。
- 最近一次发送失败后，后续相同事件可再次发送；定向探针在相同边界下从 6 次降至 4 次。

**Non-Goals:**

- 不按时间或动画帧合并不同状态；不修改现有回调来源或主进程验证。
- 不解决既有异步 IPC 请求乱序问题，也不声称真实场景中的帧率收益。

## Decisions

### 在 effect 内保存最近一次请求

`BrowserPanel` 的 `update` 读取并取整 DOM 边界后，以本次 task、session、边界和可见性组成请求，与该 effect 内最近一次已发出的请求逐字段比较。相同时直接返回；不同时立即调用原有 `setViewport`。请求发出前保存它，使尚未完成的同值请求也能去重。若该请求失败，只在它仍是最近一次请求时清空记录，允许下一次相同回调重试；较旧请求失败不得清除较新状态。effect 清理仍发送隐藏，新 effect 自行保存新记录，保持布局切换的隐藏／恢复序列。

**替代方案：**用 `requestAnimationFrame` 合并短时间内的更新，可能连不同边界的请求一并减少，但会把可见性变化延后，并要求处理卸载前取消和最后状态交付。另一个替代是在 preload 缓存请求，可减少 IPC，但会把 BrowserPanel 的生命周期状态放进公共桥接层，扩大职责和测试范围。

**最终裁决：**用户在定向探针后确认推荐的精确同值去重方案。它能直接消除已测到的重复调用，且保持变化状态立即交付；没有用户覆盖项。若必须改动 IPC 契约、隐藏时序或跨组件缓存，本设计停止并重新 Battle。

## Risks / Trade-offs

- **首个请求尚未完成时重复事件被跳过** → 把它视为同一状态的同一次交付；若请求拒绝，清空当前记录，使后续事件可重试。测试覆盖待决及失败路径。
- **旧请求失败误清除较新状态** → 用请求对象身份比对，只允许最近一次失败清除记录；测试覆盖先后两个不同边界的逆序完成。
- **主进程状态在同一 session 内被外部重置** → 当前会话生命周期由 task/session 身份驱动，effect 重新建立时会重新发送；若发现同一身份下重置，需要另行建模，不依赖重复回调充当刷新命令。
- **真实使用收益未知** → 保留“6 → 4”的合成探针计数作为验证边界，不报告未测量的用户体验改善。

## Migration Plan

无数据或接口迁移。先用定向测试确认旧实现的重复请求，再实施局部去重；若出现视图跟随回归，可撤回 BrowserPanel 内的比较逻辑，其他进程无需回滚。
