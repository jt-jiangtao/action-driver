## Context

见 [proposal.md](proposal.md)。`packages/plugin-contracts` 已校验 manifest，`packages/plugin-sdk` 已有命令、工具、Skill、面板注册和资源释放接口；Runtime 插件管理器负责原子发布与实例归属，Desktop 有插件面板宿主。新会话中的上下文键变更将提供可用条件的权威求值，本变更只消费该结果。

## Goals / Non-Goals

**Goals:**

- 六类贡献共享声明、发现、激活、实例归属与撤销规则。
- 视图和菜单能通过安全的桌面入口呈现，且直接调用与界面状态使用同一可用性结果。
- 旧插件保持有效；要求新协议的插件在旧宿主上明确失败。

**Non-Goals:**

- 不让插件直接注入渲染进程或获得原始 Electron/Node API。
- 不把贡献声明转换成任务 grants，不替代第一项的上下文键状态引擎。

## Decisions

### 扩展现有 manifest、catalog 和发布事务

新增 view/menu 定义与引用校验，保持“纯 catalog 发现，激活后原子发布”的两阶段模型；命令、工具、Skill、面板也经相同目录投影。另一方案是独立的通用 UI 注册表，它能较快展示菜单，却会与现有插件管理器形成双重所有权和停用路径，因此不采用。用户裁决覆盖完整六类贡献，接受公共契约扩张。

### 视图内容走受控宿主，菜单只绑定命令

菜单描述稳定命令 ID、位置与可用条件；视图描述容器、标题及受控内容入口。Desktop 只渲染宿主批准的贡献，视图消息沿用类型化面板桥接和安全隔离。替代方案是允许插件传入任意 React 组件或 HTML 注入主界面，但它无法维护进程与权限边界，因此不采用。

### 可用性单一来源

插件贡献声明条件，Runtime/桌面壳读取第一项上下文键服务的权威结果；菜单隐藏或禁用不能代替命令执行时校验。若第一项尚未完成，先定义可序列化条件契约与拒绝路径，再接入状态求值；不创建第二套条件语言。替代方案是各贡献类型分别维护状态判断，会导致 UI 与直接调用不一致。

## Risks / Trade-offs

- [完整六类贡献增加 manifest、SDK 与桌面协议的版本迁移成本] → 版本门槛、旧插件兼容测试和脚手架同步更新；这是用户覆盖较小首版建议时接受的代价。
- [视图扩展面可能突破渲染隔离] → 复用受控面板桥接，拒绝任意 DOM/IPC 注入。
- [菜单显示与实际授权不一致] → 直接调用在宿主再次检查条件和 grants。
- [两个规划变更同时影响插件契约] → 先稳定上下文键契约，再实现本变更；各 OpenSpec change 独立审阅。

## Migration Plan

1. 扩展契约、版本校验和脚手架，保持旧插件解析结果。
2. 扩展 Runtime 贡献目录及原子发布、撤销、诊断。
3. 接入 Desktop 视图与菜单宿主，再对接统一可用性结果。
4. 用内置与第三方样例验证六类贡献、冲突、停用和旧版本兼容；按插件协议版本发布。回滚时保留旧贡献路径并拒绝要求新版协议的插件。
