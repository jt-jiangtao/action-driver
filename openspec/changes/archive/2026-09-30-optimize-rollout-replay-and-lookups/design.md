## Context

见 `proposal.md` 的 Why。`RolloutSessionStore` 将请求保存在按 `requestId` 索引的 Map 中，但任务和幂等键查询会展开并扫描其所有值。`RolloutReadOperations.listForRequestAfter` 每次调用 `deriveRolloutEvents`，后者从会话首行折叠到末行；`StreamEventDelivery` 在实时发布和重放中按 256 条重复调用该入口。`readRollout` 一次分配剩余文件大小的 Buffer，同时会话运行时还保留解析后的行数组。当前 `rollout-persistence` 和 `runtime-event-recovery` 规范要求日志权威、顺序和残行恢复，均不得改变。

Node 24 下已有 rollout 定向测试 15/15 通过。一个仅模拟文件写入的本机探针中，500 次逐条 `fsync` 约 1.8 秒；它不包含 SQLite 投影、事件派生或真实负载，不能据此声称产品瓶颈。实施前须建立真实 store 基准。

## Goals / Non-Goals

**Goals:**

- 在固定长会话样本上降低请求查找与单请求连续续读的重复计算，并记录改动前后的中位数、P95 与内存峰值。
- 在重启、断线、追加新事件及残缺尾行后，事件顺序、标识、水位和快照与改动前完全一致。
- 派生索引可丢弃、可重建，且不会成为第二份权威历史。

**Non-Goals:**

- 不改逐条 `fsync`、日志/SQLite 格式、投影所有权、Stream 协议或用户界面。
- 不缓存二进制资产，不改变会话生命周期，也不新增跨进程服务。
- 不将浏览器图片、Monaco 或页面拆包混入本变更。

## Decisions

### 1. 以实际 store 基准决定优化是否保留

在包内加入可重复的 1、100、1000 个请求与 100、1000、10000 条事件样本，分别计量请求查找、首次续读、连续分页、重开会话和内存峰值；使用 Node 24 与同一临时磁盘，重复运行取中位数及 P95。修改前保存结果，修改后在相同环境重跑。若某项改动未使目标路径至少改善 20%，或显著增加内存峰值与写入延迟，则不以“性能优化”名义保留它；正确性修复可单独说明。

替代方案是仅凭复杂度和合成 `fsync` 探针直接重构。它不能显示真实 SQLite 与事件派生的成本，因此不采用。

### 2. 请求查找由同一所有者维护辅助索引

在 rollout store 内集中管理 `requestId` 主 Map 与 `taskId`、`idempotencyKey` 到请求的辅助映射。启动从 SQLite 投影加载时重建映射；创建、完成、恢复及更新水位时通过同一更新入口维护。保留现有重复键的首次匹配语义，不改变外部 Repository 接口。测试覆盖旧键变更、重开及幂等重复调用。

替代方案是直接给每个查询增加 SQL 查询。它会在同进程高频路径增加同步数据库往返，并让内存与数据库两套查找路径并存；目前主 Map 已存在，故先采用内存索引。

### 3. 续读派生按请求增量复用，并限制驻留

为最近使用的请求保存从日志确定性派生的事件视图和已处理会话行序号。首次读取仍从日志派生；新行追加后，仅用现有折叠状态与同一记录→事件函数补入该请求的新事件。请求元数据变化、投影重建、日志路径变化或缓存无法连续衔接时丢弃并从日志重建。只保留有界数量与字节数的请求视图；超限时回退现有完整派生路径，而不改变结果。`listForRequestAfter` 仍按既有 cursor 与 limit 返回，实时发布和重放共用这条路径。

替代方案是直接把派生事件写入 SQLite。它增加第二份持久化事件表示、迁移和一致性负担，且与现有“日志为唯一事实源”目标相悖，因此不采用。另一个替代是每页从头派生，保持代码简单但成本随页数重复增长，作为缓存失效时的安全回退保留。

### 4. 读取器只减少瞬时原始 Buffer

若基准显示全文件 Buffer 对重开内存峰值有显著贡献，将 `readRollout` 改为分块读取并保留跨块的未完成 UTF-8 行，沿用同一个 `parseRolloutLine` 与“遇到首个无效行停止”的行为。解析后的 `lines` 数组仍由现有会话状态持有；本项只解决额外原始 Buffer，不宣称消除长期日志驻留。若峰值收益不足 20%，保留现有读取器。

替代方案是引入流式惰性会话和淘汰策略，可降低长期内存，但改变运行时生命周期与重放设计，超出本批范围。

### 5. Battle 最终裁决

用户确认按推荐顺序继续优化，并要求全部在 `main` 处理。本批选择保留逐条 `fsync`，先优化索引与续读。被否决的合并刷盘方案可能提高吞吐，但会引入崩溃时最近事件丢失的窗口；桌面资源方案留作后续独立变更。现阶段没有尚未裁决的产品或架构分歧。

## Risks / Trade-offs

- [辅助索引漏更新导致查到旧请求] → 集中更新入口，比较索引查询与原 Map 扫描结果；重开后重复验证。
- [事件视图缓存与日志游标脱节] → 只在连续追加时增量补入；失配立即丢弃并完整派生，复用实时/重放等价性测试。
- [缓存提高长期内存] → 为请求数量与字节数设硬上限，基准记录峰值；超限安全回退。
- [分块读取破坏中文、换行或残行行为] → 覆盖跨块多字节字符、跨块换行、无效中间行及不完整尾行，并与现有读取器逐字节对照。
- [用户覆盖：在 `main` 实施] → 不建立隔离工作树；每次写入前核对工作区，提交仅包含本变更文件。
- [真实瓶颈可能仍是逐条刷盘] → 保留其已批准保障，报告实际测量；若需要改变保障，另起 Battle。

## Migration Plan

不迁移数据。部署后辅助索引和事件视图从已有日志/投影重建；回滚到旧代码即可，日志格式不变。
