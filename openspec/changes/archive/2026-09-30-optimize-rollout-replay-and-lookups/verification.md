# 验证记录

环境：macOS，`/opt/homebrew/bin/node` v24.20.0，Vitest 3.2.7，真实 `RolloutSessionStore`、SQLite 投影和逐行 `fsync`。固定夹具包含 1000 个请求，以及分别有 100、1000、10000 个事件的会话。命令：`PATH=/opt/homebrew/bin:$PATH corepack pnpm vitest bench apps/local-runtime/benchmarks/rollout.bench.ts --run`。

| 路径 | 修改前均值 | 索引后均值 | 最终均值 | 结论 |
| --- | ---: | ---: | ---: | --- |
| 1000 请求中的任务查找 | 0.0041 ms | 0.0006 ms | 0.0006 ms | 约快 85% |
| 10000 事件会话，从起点重复取 256 条 | 0.7911 ms | 0.8334 ms | 0.0049 ms | 连续读取约快 99.4% |
| 10000 事件会话，从末段重复取 256 条 | 0.8127 ms | 0.8514 ms | 0.0060 ms | 连续读取约快 99.3% |
| 重开并读取 10000 事件会话首 256 条 | 10.9568 ms | 11.1144 ms | 13.2922 ms | 全场景基准比基线慢约 21%，单独复测为 11.8463 ms；首次重开不建缓存，结果受前序高频分页与 GC 影响 |

Vitest 终端只报告均值、P75、P99，未输出计划要求的 P95，因此没有伪造 P95。基线 1000 请求查找 P75/P99 为 0.0041/0.0051 ms，最终为 0.0006/0.0008 ms；基线万事件起始页为 0.8048/1.0532 ms，最终为 0.0049/0.0070 ms。连续分页基准反复查询同一页，反映缓存命中成本；重开基准反映首次冷读。实际跨页与追加的等价性由定向测试覆盖。

全场景进程 RSS 峰值分别为基线 512 MB、索引后 586 MB、最终 795 MB。最终版本在极高频缓存分页中分配大量返回事件副本，导致 GC 与 RSS 峰值显著升高；这个基准的迭代次数和旧版本相差数百倍，不能直接推断正常使用下的常驻增量。`NODE_OPTIONS=--expose-gc` 下，单次建立万事件缓存前后手动 GC 后的 RSS 从 124.5 MB 到 134.4 MB（+9.9 MB，约 8%），堆使用从 27.7 MB 到 31.0 MB（+3.3 MB）。缓存限制为 8 个请求和最多 4 MiB 的序列化事件大小，超限回退完整派生。最终构建中一次单独运行的真实 store 基准里，缓存请求追加均值 5.09 ms，未缓存请求追加 6.08 ms；全场景末尾相应数字为 18.64/17.45 ms，波动较大，不能据此断言写入更快。逐行 `fsync` 保持不变。

独立代码审查发现，超限事件历史曾在每次回退读取时整段 `JSON.stringify`。审查员用生产模块做的内存样本（100 条、每条 100 KiB）测得旧完整派生约 0.067 ms/次、问题实现约 6.52 ms/次；该探针不含实际 store。修复后先逐事件计数，到上限立即停止，并记住超限请求，后续页不再做字节序列化。另修正追加事件的 JSON 数组分隔符计数，并对返回的事件外层对象做浅拷贝，防止调用方修改缓存字段。三项均有先失败后通过的定向测试。

万事件 JSONL 日志约 1,278,568 字节。即使去掉整个原始读取 Buffer，按本基准数百 MB 的进程峰值计算，也达不到预设的 20% 降幅，因此未修改 `readRollout`。

第一轮基准因长时间同步准备数据触发 Vitest 工作线程汇报超时；让准备阶段每 100 条记录让出事件循环后，基线、索引后和最终测量均正常退出。Node 20 环境的 `better-sqlite3` ABI 不匹配，所有有效测试和基准使用上述 Node 24。
