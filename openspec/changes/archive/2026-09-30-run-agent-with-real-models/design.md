## Context

参见 `proposal.md` 的 Why。前置：`serve-runtime-over-http`（服务端 HTTP/WS 与配置/凭据归属）、`implement-model-connections-service`（协议适配与错误分类，已实现并将迁入服务端）。Runtime 现有 `ModelGateway` 端口与 `DeterministicModelGateway`，以及 `plan → resolveSkill → invokeSkill → verifyOutcome` 图。

## Goals / Non-Goals

**Goals**

- 真实模型驱动规划，失败可诊断。
- 上下文最小化，历史仍只在本地。
- 同一套上层代码支持确定性与真实两条装配。

**Non-Goals**

- 不做流式增量渲染（后续增强）。
- 不做多模型协作、投票或成本优化策略。
- 不实现 Browser/Computer 真实动作（后续 change）。

## Decisions

### 1. 模型网关放在服务端，而非客户端进程
推理请求由服务端发起，凭据不出服务端。替代方案是客户端发请求：与"服务端持有凭据"的裁决冲突。

### 2. 通过模型连接解析模型
任务携带 `modelId` 与 `connectionId`（由页面模型选择器提供），服务端校验该模型处于启用状态后使用对应连接的协议适配器发起请求。替代方案是服务端自行选择"第一个启用模型"：会让用户的显式选择失效。

### 3. 上下文构造
请求包含：目标、最近 N 条消息摘要（默认 5）、可用 Skill 描述、温度与最大 token 参数。不包含完整历史与本地文件内容。替代方案是全量历史：token 成本高且与最小化裁决冲突。

### 4. 失败分类与重试
复用模型连接的错误分类；仅对限流、超时与 5xx 做最多 2 次指数退避重试；认证失败与参数错误立即失败，不重试。

### 5. 步骤投影
模型输出先归一化为计划结构（步骤标题、细节、需要的 Skill），再写入步骤仓储并发布事件；时间线读取同一投影。替代方案是把原始文本直接塞进步骤：无法保证可测试的步骤语义。

## Risks / Trade-offs

- [真实模型输出不稳定导致步骤语义漂移] → 计划输出使用结构化约定并在失败时降级为单步失败步骤；测试使用固定模型输出。
- [成本与延迟上升] → 上下文最小化 + 单次规划 + 超时上限；记录耗时与 token 计数（仅本地诊断）。
- [默认参数在不同供应商行为不一致] → 参数由连接协议适配器决定，不被上层硬编码。

## Migration Plan

1. 在服务端实现真实模型网关与测试（注入传输端口）。
2. 接线 Agent Loop 的规划节点，保留确定性装配。
3. 客户端传模型选择并展示真实步骤。
4. 运行集成与视觉验证。

回滚：把模型网关绑定切回确定性实现。

## Archive Decision (2026-09-30)

### Decisions

- 最终方向：按用户明确裁决直接归档本变更，保留 0/16 的历史任务状态，不实施剩余任务，也不同步 1 份 delta spec。
- 对比过的替代方案：先审计当前代码与各变更的依赖，完成仍有效的任务、同步规范后再逐项归档。该方案可减少遗留缺口，但需要继续执行用户现已取消的工作。
- 用户覆盖：此前建议先审计并完成有效项；用户随后明确改为整体归档，并确认当前无任务要执行。

### Risks / Trade-offs

- 未完成任务不会因归档而完成；如需这些功能，必须重新立项和验证。
- Delta spec 留在历史归档中，不作为主规范当前要求；归档不删除其他工作树中的未提交文件。
