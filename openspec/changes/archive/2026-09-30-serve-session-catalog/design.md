## Context

参见 `proposal.md` 的 Why。会话数据由本地服务端写入（见 `replace-agentd-with-local-langgraph-runtime` 的 Storage 决策），HTTP/WS 边界由 `serve-runtime-over-http` 引入；本 change 只新增目录查询与客户端接入，不改变存储布局。

## Goals / Non-Goals

**Goals**

- 让列表与历史入口消费服务端真实数据。
- 保持现有侧栏视觉、宽度与交互契约不变。
- 状态变化通过既有事件通道驱动，不引入轮询。

**Non-Goals**

- 不实现侧栏搜索、重命名、归档与批量操作（后续 change）。
- 不改变任务页布局与图形。
- 不引入新的数据表。

## Decisions

### 1. 目录查询复用任务仓储
目录摘要直接从既有 `tasks` 表派生（标题取目标、状态取当前状态、更新时间取 `updated_at`），避免新增冗余表。替代方案是新增 `session_catalog` 投影表：收益是查询更快，代价是引入第二处需要保持一致的状态。选择复用，理由是与"服务端唯一写入者 + 单一事实来源"一致。

### 2. 游标分页而非页码
用 `updated_at + id` 作为复合游标，避免翻页时因新任务插入导致条目重复或跳过。替代方案是 offset 分页，代价是插入新任务后出现重复条目。

### 3. 客户端接口异步化
`TaskCatalog` 由同步 `listRecentTasks()`/`getTask()` 改为异步（`listRecent()` / `get(id)`），`Sidebar` 与 `App` 改为在加载后渲染；Mock 实现同步返回 Promise 以保持测试简单。

### 4. 列表刷新触发
登录/启动时拉取一次，其后由会话事件（状态变化、创建、删除）触发增量更新；页面重新可见时重新拉取一次作为兜底。

## Risks / Trade-offs

- [列表与任务页状态短暂不一致] → 事件驱动 + 页面可见时兜底刷新；测试覆盖"事件到达后列表更新"。
- [会话很多时首次加载变慢] → 默认取最近 N 条（首版 20）并用游标续取；后续按需接入虚拟滚动。
- [视觉回归] → 视觉用例继续使用 mock 装配，确保布局与文案不变。

## Migration Plan

1. 服务端新增目录查询接口与测试。
2. 客户端 `TaskCatalog` 异步化并接入服务端；Mock 装配保持可用。
3. 侧栏与任务页接线，补齐加载/空/失败态测试。
4. 运行视觉与集成验证，确认布局未变化。

回滚：把 `TaskCatalog` 绑定切回 Mock 实现，服务端接口保留不影响其他能力。

## Archive Decision (2026-09-30)

### Decisions

- 最终方向：按用户明确裁决直接归档本变更，保留 0/17 的历史任务状态，不实施剩余任务，也不同步 1 份 delta spec。
- 对比过的替代方案：先审计当前代码与各变更的依赖，完成仍有效的任务、同步规范后再逐项归档。该方案可减少遗留缺口，但需要继续执行用户现已取消的工作。
- 用户覆盖：此前建议先审计并完成有效项；用户随后明确改为整体归档，并确认当前无任务要执行。

### Risks / Trade-offs

- 未完成任务不会因归档而完成；如需这些功能，必须重新立项和验证。
- Delta spec 留在历史归档中，不作为主规范当前要求；归档不删除其他工作树中的未提交文件。
