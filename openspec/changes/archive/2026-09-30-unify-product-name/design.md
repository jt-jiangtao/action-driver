## Context

见 `proposal.md`。根包已使用目标拼写；其余名称分布在数百个源文件、测试、原生 Fork、文档和历史归档中。`apps/desktop/src/renderer/src/main.tsx` 有用户已暂存的独立改动，必须保留并纳入最终提交。

## Goals / Non-Goals

**Goals:**
- 使主仓库及两个 Fork submodule 的跟踪文件内容和路径不再出现无连字符的旧品牌拼写，发布入口全部使用新名称。
- 保持更名后的 Desktop、Runtime、插件、原生 helper 与 Fork 内部引用一致。
- 把用户裁决和兼容代价纳入可追踪规格与提交记录。

**Non-Goals:**
- 不改写 Git 提交历史、上游第三方发布包或本机现存安装状态。
- 不提供旧标识的别名、迁移或自动恢复。
- 不改变产品能力和授权边界；`main.tsx` 的现有暂存改动只按用户要求并入提交。

## Decisions

### D1：完整更名而非只修改 npm 包

当前方案覆盖 `@action-driver/*`、`create-action-driver-plugin`、展示名 `Action-Driver`、协议 `action-driver:`、IPC、环境变量 `ACTION_DRIVER_*`、bundle 身份、helper、观测键、文件与目录、源代码引用和仓库文档。代码语法无法容纳连字符处，采用表达职责的合法标识符，避免机械替换导致无效源码。替代方案是仅更名 npm 作用域和脚手架，成本低且兼容面较小，但不能满足用户要求的全面一致。用户裁决采用完整更名。

### D2：破坏性切换，不保留旧名迁移层

推荐方案曾为新名称提供旧数据路径识别和迁移，保护已有会话、设置与授权。用户明确覆盖该建议，要求仓库彻底清除旧名称，接受旧数据、设置和权限可能失联。实施时不通过拆分字符串、编码或隐藏常量规避旧名扫描；新版本只使用新身份。回滚依赖恢复旧版本及其原有数据，不承诺自动双向转换。

### D3：一次性更新所有受影响边界

按依赖顺序处理包元数据及导入、桌面与 Runtime 通信、macOS helper 与 Fork、测试与文档；每个阶段用定向检查确认一致。最终以仓库跟踪文件内容和路径的大小写不敏感扫描、构建和相关运行测试验收。锁文件通过包管理器重生，生成物按仓库现有生成流程处理，不手改第三方外部依赖。历史归档文本按用户要求改写；原始 Git 历史不变。

### D4：在 `main` 提交用户已有改动

保留 `main.tsx` 已暂存的去除 `StrictMode` 变更，最终提交显式包含该文件。提交前检查工作区，若出现其他会话的新改动则不混入。按仓库规范只在准备提交时运行一次全量类型检查、lint 和测试，并在提交信息或 OpenSpec 记录中写入结果。

### D5：两个 Fork submodule 一并更名

实施中发现 Electron 和 Playwright 是独立 Git 仓库，源码与夹具中仍有旧品牌名；只改主仓库会留下可见不一致和失效的构建路径。替代方案是保持两个 submodule 内部旧名称，仅修改主仓库；成本较低，但不满足用户再次确认的“全部”范围。用户裁决纳入两个 submodule：分别改动、定向验证并创建本地提交，更新主仓库 gitlink 与锁定 commit。推送是对外写操作，先展示可审查的本地提交和验证结果，再执行推送。

## Risks / Trade-offs

- [旧用户数据、浏览器配置、系统授权、插件安装可能无法复用] → 用户已接受；文档说明新身份与重新授权需求，不写旧名迁移代码。
- [包名和协议变更会使外部调用方、已发布插件和脚本失效] → 新规范、脚手架和示例同步更新；不承诺兼容别名。
- [原生 Fork 路径和 bundle 身份变更可能导致构建或签名失败] → 定向验证原生构建与打包产物身份，提交前按需运行打包验证。
- [历史归档改写会失去原文可读性] → 用户明确要求；Git 历史仍可追溯原文。
- [大范围机械编辑可能遗漏字符串、路径或误改源码符号] → 基于跟踪文件与路径做大小写不敏感扫描，再以类型检查、定向测试和打包验证覆盖引用关系。
- [主仓库 gitlink 若指向未推送的 submodule 提交，其他人无法获取] → 先完成本地修改与验证，审查后推送两个 submodule，再提交主仓库；不可推送时不得发布不可获取的 gitlink。

## Migration Plan

1. 在 `main` 上完成完整更名及文档更新，保持用户现有 `main.tsx` 暂存改动；两个 Fork 分别创建本地提交并更新锁定记录。
2. 新版以新包名、应用身份和数据路径启动；不读取或复制旧身份状态。用户可能需重新配置和授权。
3. 两个 Fork 的本地提交与主仓库 gitlink、锁定记录一同审查；获准推送后确认远端可获取，再进行提交前一次性全量验证并提交主仓库。
4. 如需回滚，恢复旧提交和原应用版本；新身份产生的状态不自动转回旧版。
