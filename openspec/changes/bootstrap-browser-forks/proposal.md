## Why

两个 submodule 已能拉取源码，但必要构建输入仍依赖本机被忽略的配置、依赖和手工步骤。需要受 Git 管理的统一入口，使全新 macOS arm64 工作区能够准备环境、构建双 Fork、导出产物并完成桌面打包验证。

## What Changes

- 固化源码、工具版本、gclient 与 GN 模板及依赖获取方式；保留直属源码与独立构建工作区布局。
- 提供分阶段统一命令，贯通源码初始化、环境检查、依赖同步、编译、产物导出、来源生成与验证。
- 自动生成独立 Node 包边界及本机来源记录，不沿用其他机器的产物哈希或绝对路径。
- 打包阶段复用现有 Electron 原生模块、Computer Use helper 和桌面打包验证入口。
- 用不含本机 thridparty、node_modules、out、dist 的全新检出完成验收，记录实际阶段结果与失败原因。

## Capabilities

### New Capabilities

- `browser-fork-build`: 定义锁定输入、从新检出构建、阶段恢复、产物来源和打包验证的命令行为。

### Modified Capabilities

无。

## Impact

主仓库构建配置、脚本、来源解析器、开发文档及两个 Fork 的自有验收夹具。必要自有源码必须提交至对应 Fork，并确保主仓库指针能从远端获取。构建缓存、工具安装目录与二进制仍被忽略，不增加 Chromium submodule。

## Battle Status

- 类型：构建与来源管理架构决策型；用户已确认统一入口及全新工作区验收目标。
- 最终方向：受 Git 管理的输入与阶段脚本，下载和生成依赖，完成真实源码构建及打包验证。
- 替代方案：只维护手动命令文档；实现成本较低，但不能自动检查本机缺失配置、源码漂移和阶段完成情况。将全部工具和二进制入 Git 能缩短准备时间，但仓库成本高且不能证明源码编译，故不采用。
- 检查结论：submodule 仅覆盖源码；包边界、工具版本、配置和来源生成逻辑必须可复现。没有实质性异议。
- 主要风险：新工作区首次下载和编译成本高，需有效 Xcode/SDK/Metal；外部下载与依赖安装可能失败。固定源码不保证二进制逐字节一致，必须生成真实本机来源记录。
- 范围：首期 macOS arm64，不安装或升级系统 Xcode，不新增水印行为；水印由独立变更管理。
