## Context

见 `proposal.md` 的动机。`BrowserPanel` 通过现有 preload API 发送四个整数边界和可见性；`manager.ts` 校验可信发送方、任务归属及数值；`embedded-host.ts` 保存当前视口，并在每次 `setViewport` 中调用 `syncViews`。新建、切换和关闭页签也各自调用 `syncViews`，因为活动页签变化必须立即反映到 Electron 视图。

## Goals / Non-Goals

**Goals:**

- 相同的连续视口请求不再重复调用页签视图的 `setBounds` / `setVisible`。
- 边界或可见性变化、活动页签变化和新页签创建仍立即同步。
- 用定向测试计数验证调用减少，并确认最终视图状态相同。

**Non-Goals:**

- 不合并或节流渲染进程的 IPC 发送；本变更不宣称 IPC 数量下降。
- 不改变 Browser Session 的授权、请求结构、会话归属或导航行为。
- 不承诺未经运行时 profile 证明的帧率或延迟收益。

## Decisions

### 在宿主的 `setViewport` 入口比较状态

比较已保存的 `x`、`y`、`width`、`height` 和 `visible`；五项均相同则直接返回。若任一项不同，复制边界、更新可见性并沿用现有 `syncViews`。先执行现有开放状态与数值校验，再判断是否重复，避免去重绕过错误检查。页签新建、切换和关闭继续直接调用 `syncViews`，不使用该视口去重条件。

**替代方案：**在 `BrowserPanel` 合并 `ResizeObserver` 和窗口 `resize` 的回调，或按动画帧节流。它能减少 IPC，但需要处理卸载隐藏、布局切换和回调时序，可能延迟视图跟随。本轮缺少实际 IPC 频率测量，因此暂不改渲染侧。

**最终裁决：**用户确认采用主进程宿主去重；没有覆盖 Agent 推荐。保持现有 IPC 边界和可见行为。选择此方案的依据是局部、可逆，且可用视图方法调用次数直接验证。重新开启条件是定向测试表明页签切换受影响，或实际测量显示主要开销在 IPC 而非视图方法。

## Risks / Trade-offs

- **重复请求中隐含的强制刷新语义可能丢失** → 当前调用方只传视口状态，没有刷新意图；测试覆盖新建、切换和关闭页签的独立同步路径。若后续出现显式强制刷新需求，应另行设计，不借用重复请求。
- **同值请求仍经过 IPC 与 manager 校验** → 本轮只减少宿主视图调用，不将其描述为端到端性能提升；必要时另行测量 IPC 并开启后续优化。
- **并行工作区修改影响全量校验** → 本变更只暂存自己的文件，记录与本变更无关的失败，不修改其他会话正在编辑的代码。

## Migration Plan

无数据迁移。按定向测试确认后正常提交；若发现布局或页签可见性回归，可单独撤回宿主的状态比较而不改变 IPC 契约。
