## Context

见 proposal.md。现有实现仅在模型主动调用内部活动更新时建立时间线；普通工具流和快照投影缺少活动事实来源，Renderer 因而显示旧工具卡。

## Goals / Non-Goals

**Goals:**

- 让每个真实工具工作阶段呈现为一个含 `n` 条工具的活动任务。
- 让实时流、重连和快照恢复共享同一活动过程。
- 令任务页只使用 Codex 风格的扁平活动行、展开式原始 I/O 和完成归档。

**Non-Goals:**

- 不公开模型原始思维链，不变更工具权限或模型提供商协议。
- 不定义完整 LLM 调用日志的保留和脱敏策略。

## Decisions

### Runtime 生成受控兜底活动

Graph 在任务启动时生成稳定的默认活动（`正在处理请求`），并在同一连续工作阶段内复用该 id；因此初始等待、无工具任务和每条工具都有活动归属。活动标题只能由 Runtime 原位修订，不能另建未关联活动；规则无法生成标题时仍由默认标题兜底。这样一条任务容纳 `n` 个工具，且工具调用不再各自成为卡片。替代方案是在 Renderer 按工具类型或相邻事件猜测分组；这会在重连时不稳定并违背 Runtime 是唯一事实来源的边界。用户已确认 Runtime 聚合。

每次外部工具实际启动前，Graph MUST 以更高的 `titleRevision` 将当前活动标题更新为由工具类别和安全参数映射的动作（例如“正在读取文件”“正在搜索网页”“正在执行命令”）。Graph 不向模型提供 `activity_update`，也不生成合成工具结果；若此前活动已完成，Graph 先创建新的受控活动再执行该工具。替代方案是保留模型元工具或增加单独的标题 LLM 调用；前者无法保证覆盖率，后者增加延迟和失败面。用户裁决采用运行时规则，接受标题可能较泛化的风险。

### 持久化 cursor 是正文与工具的唯一顺序

所有过程事件在发送给 Renderer 前先持久化；单任务写入被串行化。持久化 `cursor` 决定正文片段、活动更新、工具首次出现和工具状态更新的先后，不使用发生时间或事件到达时间重排。工具记录携带稳定 `callId` 和执行时的 `activityId`；首个工具事件决定展示位置，后续 I/O 更新原行。并行工具的完成顺序按实际持久化顺序记录，但已出现的工具行不因完成时间移动。

模型流正文先作为当前调用的待定文本项，模型调用结束时根据是否继续调用工具将其归入过程正文或最终结论。过程正文与工具共享同一顺序投影；累计助手消息只保存会话内容，不再次独立渲染为过程。现有 `cursor` 已提供顺序，因而不新增 `sequenceNumber`、`outputIndex` 或 `contentIndex` 等冗余字段。

### 快照携带活动过程投影

快照同时返回活动组、按 cursor 排列的活动正文/工具引用和每条工具的原始 I/O 边界。快照与实时流使用同一纯投影器；快照在一致的高水位 cursor 上构造，之后仅应用更大的 cursor，重复事件不再添加项目。替代方案是恢复后重放或重算历史；前者受事件保留期限制，后者会改变标题与顺序。选择快照投影以确保重新打开任务后与实时界面一致。

重新打开任务走桌面 `task.get` RPC，而不是 WebSocket 重连。该 RPC 必须按任务 ID 读取同一持久化快照，并把活动组、时间线、工具 I/O 和结束用时合入 `TaskProjection`；否则实时正确而新窗口仍为空。流任务的中断则通过对应的 stream cancel 请求完成，使审批中断、任务终态和前端卡片保持一致；旧非流任务保留 RPC 中断路径。

新任务的 `task.get` 响应可能与已经缓冲的 WebSocket 事件重叠。因此 `TaskProjection` 同时携带该快照的 `streamCursor` 与现有响应 `streamSequence` 高水位；Renderer 只应用更大的持久化 cursor，并从已确认的 sequence 继续接收正文，避免启动时重复追加文本。这两个值是恢复检查点，不是新增的展示排序字段。

### 移除 Runtime 任务的旧卡回退

Runtime 驱动任务总是渲染活动时间线；空过程仅显示“正在思考”或完成结论。替代方案是保留旧卡作为缺失活动时的容错 UI；它正是本次回归的可见原因，且与 Codex 视觉规则冲突。

## Risks / Trade-offs

- [默认标题较泛化] → 工具实际启动前由 Runtime 规则更新；规则失败时保留安全默认标题。
- [规则标题较泛化] → 接受用户裁决；确保标题准确描述工具动作，不凭空推断任务意图。
- [并行工具输出顺序不确定] → 固定各工具的首次出现位置，后续输出只更新所属工具；事件按实际持久化顺序保留。
- [快照负载增大] → 复用既有原始 I/O 上限和截断标记，且只投影单任务所需过程。
- [旧任务没有活动历史] → 对遗留数据构造受控恢复活动，避免展示旧类别卡。

## Migration Plan

1. 用失败测试固定普通工具流和快照恢复的回归。
2. 在 Runtime 中写入兜底活动和完整快照投影。
3. 将 Desktop 统一到活动时间线，移除旧卡分支并做视觉 E2E 验证。
4. 若发生回归，保留事件与快照数据但回滚 Renderer 的新样式；不恢复固定类别卡作为长期路径。
