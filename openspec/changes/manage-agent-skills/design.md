## Context

参见 `proposal.md` 的 Why。既有约束：`agent-skill-boundary` 要求 Agent 通过统一 Skill 契约调用能力、Browser 与 Computer 独立注册；主提示词与 Skill 已明确要求存放在 `~/.action-driver`，不进入数据库；页面通过窄桥或本地服务接口访问能力，不直接拥有任意文件系统权限。设置侧栏已经包含模型连接与日志，现有 `manage-agent-skills` 规划原本把 Skills 作为独立顶层页面，本次裁决将其迁入统一设置区域并增加全局主提示词。

## Goals / Non-Goals

**Goals**

- 建立由 Runtime 受限文件服务持有的全局主提示词与 Skill 目录，使任务启动和设置页读取同一份文件事实。
- 在设置侧栏提供一致的主提示词和 Skills 管理体验，并保留应用主侧栏 Skills 快捷入口。
- 保持内置 Skill、自定义声明和已注册执行器的清晰边界。
- 让 Markdown 编辑预览与后续模型回复、日志正文共享安全渲染原则。

**Non-Goals**

- 不实现 MCP（仅保留入口）。
- 不实现自定义 Skill 的沙箱执行、市场分发或版本升级。
- 不改变 Agent Loop 的调用契约。
- 不在首版提供多个 Agent、模型级或任务级主提示词，也不提供数据库版本历史。
- 不删除测试专用 Mock；只禁止生产组合根使用页面内置 Mock 作为数据来源。

## Decisions

### 1. Runtime 通过受限文件服务持有 Agent 配置
主提示词固定存放在 `~/.action-driver/prompts/main.md`，Skill 固定存放在 `~/.action-driver/skills/<skill>/`。Runtime 独占应用内写入能力，Renderer 通过类型化服务枚举目录、读取文件和原子保存；Runtime MUST 拒绝越出上述根目录的路径。数据库、`localStorage` 和额外 JSON 注册表均不保存这些内容，避免与用户可直接查看和编辑的文件形成双重事实来源。

### 2. 主提示词首版使用稳定单例
主提示词使用稳定路径保存单个全局 Markdown 文件；保存采用临时文件加原子替换，页面维护未保存草稿，任务仅在启动时读取最近一次成功保存的内容。替代方案是首版支持提示词档案及 Agent/模型/任务覆盖优先级，但会显著扩大页面、合并规则和迁移复杂度，因此后置。

### 3. Skill 以目录与文件为事实来源
每个 Skill 是 `~/.action-driver/skills/<skill>/` 下的目录，`SKILL.md` 为主要声明文件，可包含 references、scripts 等子目录。页面允许通过文件树查看与编辑目录中的文本文件；非 Markdown 文本使用 Monaco。文件存在不代表可执行；普通说明型 Skill 可以启用，可执行工具仍需 Registry 与 Policy Gate 授权。

### 4. 设置区域是唯一管理入口
设置侧栏按“模型 / Agent / 诊断”分组：模型连接；主提示词、Skills；日志。应用主侧栏 Skills 只作为跳转到设置 Skills 的快捷入口，不维护第二套路由状态或页面实例。替代方案是继续保留顶层 Skill 工作区并只把主提示词放在设置，会让配置入口分裂，因此不采用。

### 5. Markdown 使用单编辑面板实时渲染
主提示词与 `SKILL.md` 使用同一个可编辑 Markdown 面板，编辑时直接渲染标题、列表、代码块和链接，不创建并排的第二个输入框；需要处理原始 Markdown 时，在同一面板切换到 Monaco 源码模式。渲染器默认禁用原始 HTML、脚本和不受信任协议。非 Markdown 文本直接使用 Monaco。

### 6. 生产与测试组合根保持可替换
生产组合根必须绑定 Runtime 的真实本地服务；组件、视觉和集成测试可以注入实现同一接口的确定性替身。替代方案是彻底删除所有 Mock，但会迫使 UI 状态测试依赖真实数据库、模型密钥和网络，降低稳定性，因此不采用。

### 7. Battle 最终裁决
Battle 已完成。用户明确选择方案 A：Runtime 受限文件服务；`~/.action-driver` 为唯一事实来源；全局唯一主提示词；Skill 文件目录与已注册执行器分离；设置为唯一管理入口；生产路径去 Mock、测试替身保留。视觉复核后用户明确覆盖原 Primer 优先裁决：以已确认生图为结构基准，组件复用不得降低还原度；日志页随后明确裁决采用 Codex 式简约内容区，保留统一设置侧栏，右侧改为纯白并使用中性灰分隔。无未解决分歧。

### 8. 设置内容区采用 ActionDriver 生图还原布局
所有页面引用同一套既有 248px 设置侧栏，只改变激活项，禁止出现第二种侧栏主题。Figma 文件使用独立的 `04 Model Configuration`、`05 Agent Configuration`、`06 Logs` 页面管理模型配置、Agent 配置和日志状态；应用内仍通过同一设置导航访问。右侧内容保留约 34px 起始边距与约 30px 结束边距；标题操作区、路径栏、编辑器工具栏、筛选栏、表格、分页和抽屉分别使用页面内局部 Auto Layout。日志页内容区采用 Codex 式纯白画布、低对比中性灰边框与分隔线，蓝色只承担选中态、主操作和链接，展开抽屉同样使用白底；成功、运行、失败继续使用语义色。主提示词保持单面板实时渲染；Skills 详情保持左侧文件树与右侧单编辑面板。组件只在视觉和交互完全匹配时复用，不得为了组件化改变生图的密度、按钮形态或信息层级。

Agent 配置稿采用同一 Codex 式纯白内容区并整体重写，删除重复版本。状态集收敛为主提示词 7 态、Skills 列表 3 态、Skills 编辑器 5 态。确认类模态框统一为 480px 宽，创建 Skill 表单为 520px 宽，历史抽屉为 420px 宽；图层顺序必须是基础页面、遮罩、浮层，模态框在视口居中，抽屉贴右并与内容区边界对齐。浮层高度由内容和统一内边距决定，操作区固定在底部，不允许按钮悬空或遮挡正文。

Agent 配置页使用克制的层级阴影：编辑器、列表等主内容容器仅使用低透明度近距离阴影；菜单和模态框使用中等悬浮阴影；历史抽屉只使用朝左的单向阴影；普通表格行和按钮不添加装饰性阴影。保存按钮按状态统一：已保存为中性灰禁用，未保存为黑色可用，保存中为灰色禁用并显示进度文案，保存失败保留红色错误状态并提供黑色“重新保存”操作。

模型层日志详情沿用相同的 Codex 层级原则。设置侧栏固定为 248px 时，右侧 `Main Content` 必须恢复为完整的 1192px 宽度，禁止因子容器宽度错误裁掉详情内容。摘要、调用导航和调用详情使用白底、浅灰边框与低透明度近距离阴影；普通披露行保持扁平，仅在菜单、抽屉或模态框出现时提升阴影等级。

模型配置空状态使用白色卡片、浅灰边框与低透明度近距离阴影；“添加模型集”等主操作统一为黑色按钮，协议文档等次级跳转保留蓝色链接。组件实例本身不得通过新增不透明填充遮挡内部文案；需要卡片背景时，应在实例背后使用独立背景层，并保持组件内容位于更高图层。

模型选择下拉必须区分持久选择与瞬时交互。模型项使用 `Normal`、`Hover`、`Pressed`、`Selected`、`Selected Hover`、`Focus Visible` 六种明确状态；连接项使用 `Normal`、`Hover`、`Pressed`、`Focus Visible`，并与展开/收起维度正交组合。`Selected` 是唯一持久选中态并显示勾选，`Pressed` 仅代表指针按下瞬间，禁止以 CSS `:active` 或名为 `Active` 的持久状态实现选择。页面静态稿只展示 `Selected + Normal`，Hover、Pressed 与 Focus Visible 仅在组件状态契约中分别展示，避免开发把多个视觉反馈误判为并列选中。

### 9. 全页面交互完整性采用“状态契约优先”
全量审计覆盖 Foundations、Components、Home、Task、Model Configuration、Agent Configuration 与 Logs。最终裁决采用方案 A：先统一基础组件的交互状态和命名，再补页面结果状态，最后连接 Figma Prototype 并做视觉回归；不得先在页面复制临时 Frame 按钮。交互组件统一使用 `Normal`、`Hover`、`Pressed`、`Focus Visible`、`Disabled`、`Loading` 等瞬时状态；持久状态使用 `Selected`、`Open`、`Applied`、`Expanded` 等结果语义，禁止用 `Active` 同时表达按下、选中和菜单打开。

Icon Button、Sidebar Entry、Recent Task、Model Selector Trigger、Checkbox、Radio、Select、Switch、Tabs、Pagination、Accordion 与日志筛选项必须形成可复用状态契约。Agent 和日志页面中现有普通 Frame 按钮应替换为组件实例，但页面视觉还原优先；组件 API 与生图不匹配时扩展本地组件，不引入 Ant Design 的视觉层。每个可操作节点必须满足二者之一：连接到明确的页面/浮层结果状态，或声明为瞬时外部副作用并提供成功/失败反馈。全文件最终不得保留无目标的主要按钮，Prototype 必须覆盖页面内导航、打开/关闭、确认/取消、前进/返回与核心状态切换。

Codex 视觉基线固定为白色内容区、中性灰边框、黑色主操作、蓝色仅用于选中/焦点/链接、语义色仅用于成功/运行/失败；普通按钮和表格行不使用装饰性阴影。模态框、菜单和抽屉使用克制悬浮阴影，圆角、控件高度、下拉箭头和间距由同一组件契约控制。模型配置遗留的蓝色主按钮、日志多套下拉样式和跨页不一致的按钮尺寸必须在页面回归阶段统一。

### 10. Skill 声明通过 `executor` 显式映射运行时能力
`~/.action-driver/skills/<skill>/SKILL.md` 的 frontmatter 可以声明 `executor: <runtime-skill-id>`，用于既有执行器映射。目录名继续承担用户可读的配置标识和文件路径；二者不得通过同名约定隐式绑定。普通 Skill 的启用不要求 executor，任务启动时读取已启用目录的摘要；工具调用仍经过 Tool Registry 与 Policy Gate 校验。后续具体实现见 `install-instruction-skills-and-run-inline-scripts`。

内置映射保留既有目录并显式声明：`browser-tools` 映射 `browser-use`，`computer-tools` 映射 `computer-use`。没有可执行器的 `report-writer` 与普通自定义 Skill 作为说明型 Skill 可启用；映射不授予任何工具权限。

替代方案是强制目录名等于执行器 ID，并把 `browser-tools` 迁移为 `browser-use`。该方案减少一个字段，但会破坏既有用户目录、耦合展示名称与内部协议，并使未来一个执行器支持多个声明时再次迁移，因此不采用。显式映射的代价是需要解析 frontmatter，并在 Main 与 Runtime 之间携带每次任务的能力快照；该成本换取了稳定文件路径和明确权限边界。

## Risks / Trade-offs

- [全局主提示词未来扩展为多个配置时需要迁移] → 保留稳定默认路径，未来增加清单文件但不改变 `main.md` 的含义。
- [用户误改主提示词导致任务行为异常] → 显式保存、未保存离开确认、恢复默认值，并在保存失败时保留草稿。
- [Markdown 内容带来注入风险] → 禁止原始 HTML 与脚本，限制链接协议，渲染器使用统一安全策略。
- [自定义 Skill 描述与实际执行能力不一致] → 说明型 Skill 不授予执行权限，实际工具调用由 Registry 与 Policy Gate 校验。
- [任务启动后 Skill 状态发生变化] → 任务请求携带启动时摘要快照用于可重复规划；按需读取再次校验当前启用状态，工具调用仍由独立策略复核。
- [`executor` frontmatter 拼写错误或未知] → 不隐式回退目录名，也不授予能力；普通说明内容仍可按有效 `SKILL.md` 启用。
- [外部程序修改文件导致页面草稿冲突] → 读取文件修改时间或内容摘要；保存前检测冲突并允许重新加载或另存。
- [路径穿越或符号链接越界] → Runtime 规范化并校验真实路径，拒绝越出 `~/.action-driver/prompts` 和 `skills` 的访问。
- [生产路径意外回退 Mock] → 组合根测试断言生产绑定为真实服务，空数据展示空状态而不是示例数据。
- [新增页面引发视觉回归] → 复用设置页 Token 与组件语义，并对加载、空、编辑、保存、失败、确认等状态做视觉验收。

## Migration Plan

1. 创建 `~/.action-driver/prompts` 与 `~/.action-driver/skills`，仅在目标文件不存在时写入默认主提示词与内置 Skill。
2. 实现受限文件服务与类型化接口，验证路径边界、重启恢复、原子写入、冲突检测和失败回滚。
3. 将生产组合根接入真实服务，同时保留测试组合根的确定性替身。
4. 实现设置导航、主提示词与 Skills 页面，再接线应用主侧栏 Skills 快捷入口。
5. 运行组件、视觉、集成和生产组合根验证。

回滚：隐藏新增设置入口并停止调用写接口；保留用户已保存的 `~/.action-driver` 文件，不做自动删除。
