## Why

当前对话把所有助手文字固定放在全部生成图片之前。生图工具执行后产生的最终文字因此显示在图片上方，且多次生图调用只凭图片完成顺序无法表达稳定的批次位置。用户需要图片和最终文字按实际调用顺序展示，并在运行、恢复及历史会话中保持一致。

Battle 已完成。用户明确选择“按调用顺序穿插展示、批内按请求编号排序”，而非把全部图片统一置顶；过程文字继续归档。主要风险是需要调整消息内容与流事件协议，旧记录已丢失的原始时序无法恢复；用户接受旧记录按现有持久化顺序展示。无未裁决的关键分歧。

## What Changes

- 生图调用进入运行态时，为该调用在助手内容中固定批次位置和 1–16 个图片插槽。
- 图片完成后只更新对应调用和索引的插槽；多个批次始终按调用顺序显示，最终文字按其生成位置显示。
- 流事件、快照、本地持久化和历史展示保留同一内容顺序；旧消息缺少批次位置时按已有记录顺序兼容展示。
- 保留过程文字归档、用户上传图片气泡顺序及不传输图片字节的约束。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `conversation-images`: 将生成图片和最终文字的固定“文字在上”规则改为按生图调用位置穿插，定义多批次、插槽和旧记录行为。
- `runtime-event-recovery`: 明确批次位置事件与助手内容原子持久化，并在事件重放和快照恢复时保持顺序。

## Impact

涉及 `packages/contracts` 与 `packages/runtime-contracts` 的消息部件和流事件、`apps/agent-runtime` 的持久化与事件发布、`apps/desktop` 的流投影和对话渲染，以及对应测试与主规范。无需新依赖、数据库表、提供方 API 或图片文件目录变更。
